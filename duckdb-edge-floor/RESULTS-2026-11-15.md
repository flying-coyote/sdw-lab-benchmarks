# DuckDB edge floor under an enforced memory cap (2026-11-15)

**Rig stamp (methodology §7b).**

- Host: Beelink (Ryzen 7 5800H), WSL2 kernel 6.6.87.2, 14 vCPU, about 47 GB, under Docker 29.5.3 (server 29.8.0, cgroup v2).
- Software: DuckDB 1.5.3 on Python 3.12.3, in image `sdw-edge-floor:duckdb-1.5.3` (`sha256:ead733f4...558943`).
- Run windows:
  - main arm, 2026-11-15 20:00:24Z to 23:18:59Z;
  - arm B, 23:29:05Z to 2026-11-16 00:18:02Z;
  - arm C, 00:24:40Z to 00:29:41Z.
- Clock: chrony, with the `chronyc tracking` offset checked on every trial. It ranged from -1.40 s to +0.0005 s across the main arm, -0.24 s to +0.0001 s across arm B and -0.27 s to +0.0001 s across arm C. The larger readings were transient, and durations use the monotonic `perf_counter`.
- Windows power plan: not checked this run.
- Timings are hot/warm, and the main arm and arm B ran under contention from other jobs (see deviation 5). Treat those latencies as indicative; the memory outcomes are the result. Arm C ran at a 1-minute load of 0.2 to 1.6, so its timings are the cleanest here.
- Tier B, single host, synthetic data.

**Units.** Caps are Docker `--memory=<n>m`, which is MiB, and every memory figure in the tables is MiB (2^20 bytes). DuckDB parses `memory_limit='224MB'` as decimal megabytes, so its limits are about 4.6% smaller in MiB than the nominal fraction implies (see deviation 8).

This run answers items 1 to 5 of "What's missing before this can publish" in draft 18 (`project1/02-projects/securitydataworks/content/drafts-2026-11/18-hunting-at-the-edge-duckdb.md`). Item 6, real edge hardware, is out of scope: everything ran on the Beelink under Docker, so an ARM or industrial-PC pass with a cold cache is still owed.

## Headline

*Read with the corrections at the end (2026-11-15): the frozen result, a 256 MiB floor for S and H under the 7/8 rule with kernel OOM kills below it, is the primary finding; the 64 and 128 MiB floors below are post-hoc.*

**Floors under an enforced cap, at threads 1, at the best `memory_limit` tried:**

- **S**, the streaming two-level UEBA aggregation, has a floor of **64 MiB**, with `memory_limit='32MB'` (30.5 MiB).
  - It holds on U, Z and Z2.
  - It completes in 1.8 s against 0.68 s uncapped on Z2 at low load (2.7×), spilling 139 MiB.
  - Peak anon is 59 MiB.
- **H**, the heavy group-by, has a floor of **128 MiB**, with `memory_limit='64MB'` (61.0 MiB).
  - It holds on U, Z and Z2.
  - It completes in 5.2 s against 2.3 s uncapped on Z2 (2.2×), spilling 561 MiB.
  - Peak anon is 91 MiB.
  - At 64 MiB DuckDB refuses it with an out-of-memory error.
- **J**, the self-join, has **no floor at or below 256 MiB**.
  - It completes only at the 4096 MiB reference, which used 1.2 to 2.8 GiB anon depending on corpus.
  - Every capped point tried ends in a kernel kill or a DuckDB out-of-memory error.

These floors come from the post-hoc arms B and C, not from the frozen hypotheses. They are lower bounds on device memory (see the accounting caveat), and they hold only at the one `memory_limit` working point found. They come from a three-fraction sweep, so they don't amount to a tuning rule.

**Main arm, as frozen: the draft's "just below the cap" rule fails.** It set `memory_limit` at 7/8 of the cap, which is 83% in MiB terms. Under that rule:

- The floor was 256 MiB for S and H at one thread, on U and Z. Z2 was not run at 128 MiB under this rule.
- J did not complete at 256 MiB.
- No shape completed at 256 MiB with four threads.
- In all 12 failing shape chains the failure was a **kernel OOM kill**, and DuckDB never raised its own error.

The June figures "completes at 128 MB" and "at 64 MB" were `memory_limit` settings on a 47 GB host. Under an OS cap of those sizes, with the 7/8 rule, every shape was killed.

**Spill exists and is large.** Live polling saw up to 561 MiB of temp files in completed runs and 1,012 MiB in a failed J run. The files exist during execution and are gone afterwards:

- June's check ran after `fetchall()` with the connection still open, and found the directory empty.
- Here, the directory was checked after process exit: 0 of 205 completed trials, and 0 DuckDB-refused trials, left a file behind.

I did not measure the directory at the exact moment the query returns, but the two checks together explain why June never saw spill. Only killed processes left spill on disk.

**Why the 7/8 rule fails.** The buffer manager fills to its limit; in the 256 MiB cells it peaked at 213.6 to 213.9 MiB, which is the `'224MB'` setting. The process's anonymous memory runs 21 to 35 MiB above the buffer manager. About 18 MiB of that is the Python + DuckDB client, measured in the null cells, and the rest is query allocations outside the buffer manager. So a limit at 83% of the cap leaves too little room. At roughly half the cap, the query spills and completes. Lower than that, DuckDB fails fast and cleanly with its own `OutOfMemoryException`.

## Arm C (addendum B, post-hoc): corpus Z2 with independent keys

After the main arm and arm B, a check prompted by the J-Z answer (only 850 distinct host-process-pair rows from 50.4 M co-occurrences) showed that **corpus Z's keys are not independent**.

- Its generator used `hash(i, '<column>')`, and in DuckDB 1.5.3 `xor(hash(i,'a'), hash(i,'b'))` is the same constant for every `i`, so each Z column is a function of `hash(i)`.
- In consequence, the head host `h0` has only 12 distinct processes and 19 users, and the whole corpus has only 8,359 distinct host-process pairs.

Addendum B (frozen 00:24:28Z, before Z2 existed) generated **Z2**: the same Zipf mapping, with each column hashing a distinct integer, `hash(i * 8 + k)`. In Z2, `h0` has 200 processes, 19,938 users and all 10,081 minutes, and there are 890,549 distinct host-process pairs.

## What the samples show about the mechanism

These figures come from the last poll sample before each kill, at threads 1, trial 1 (`trials.jsonl` `last_sample`).

- **S on U at the 128 MiB cap, 7/8 rule.** At the kill, 1.28 s into the container's life:
  - The buffer manager was at 106 MiB, which is its `'112MB'` limit (106.8 MiB).
  - cgroup anon was at 124 MiB.
  - 2.4 MiB had just spilled.
  - The client's 18 to 20 MiB plus a full buffer manager is already the whole cap.
- **H and J at 128 and 64 MiB.** The same pattern, with anon 7 to 19 MiB above the buffer manager at the moment of death. J at 256 MiB is the exception: it spilled 491 MiB (U) and 527 MiB (Z) over 6 to 8 s before it was killed.
- **Completed 256 MiB trials that spilled (S-U, H-U, H-Z, H-Z2).**
  - The buffer manager sat at its limit, 213.6 to 213.9 MiB.
  - Peak anon ran 25 to 35 MiB above it, against 21 to 23 MiB in the non-spilling S-Z and S-Z2 cells.
  - `VmHWM` was 281 to 291 MiB, which is over the cap, because `VmHWM` counts file-backed library pages the cgroup did not charge.
  - This is the draft's second explanation, measured: `memory_limit` bounds the buffer manager, not the process.
- **DuckDB fills toward whatever limit it is given.** S on Z needed 78 MiB of buffer manager uncapped, but reached 106 MiB at the 128 MiB cap before the kill, and 122 MiB at 256 MiB with `'128MB'` on Z2.

### Accounting caveat (bears on every floor above)

`memory.peak` counts only pages first touched inside the container.

- On the null cells, `memory.peak` read 20.2 MiB while `VmHWM` read 59.0 MiB, because the DuckDB library's pages were already in the host page cache, charged to an earlier cgroup.
- A one-off check in a fresh 64 MiB container (`memory.stat` anon 16 MiB, file 23 MiB, `file_mapped` 18 MiB; `RssFile` 36 MiB) confirms that part of the client's file-backed footprint is not charged to the container.

On a real device, every page counts. So the 32 MiB client floor is optimistic, and every floor here is a lower bound on device memory, probably by something like 13 to 40 MiB. The Parquet page cache is reclaimable, and it was charged when touched, which is why `memory.peak` sits at the cap in the 256 MiB cells while the trial still completes.

## What this changes in draft 18

- **"Runs in 128 MB / 64 MB" cannot stand as device-memory claims.** Under an OS cap of those sizes, with the limit just below the cap, every shape was killed. Two things can be said:
  - The June shapes complete with DuckDB's `memory_limit` at those values on a large host.
  - Under an enforced cap, the streaming detection completes at 64 MiB and the heavy group-by at 128 MiB, both spilling to disk, but only with `memory_limit` near half the cap. This was one working point found in a three-point sweep, and a lower bound on device memory.
- **"Graceful degradation" needs qualifying.** With the limit just below the cap, the failure is a kernel OOM kill with no error from DuckDB. A lower limit turns most kills into a fast, clean DuckDB out-of-memory error.
- **The three Tier D explanations are now measured:**
  - Temp files are deleted before a post-query check: supported. They existed during execution and were gone after process exit; June's check after `fetchall()` also found them gone. The exact moment of deletion was not measured.
  - Allocations sit outside the buffer manager: held. Anon ran 21 to 35 MiB above it, about 18 MiB of that the client.
  - Compact aggregate state: not supported for H, which spilled 450 to 560 MiB. S on the skewed corpora fit without spilling.
- **The co-occurrence self-join is the shape to warn about.** It needed 1.2 to 2.8 GiB uncapped, and it did not complete at 256 MiB under any setting tried.

## Note added 2026-11-16: DuckDB's documentation on `memory_limit`

Appended after a review; nothing above is changed. Neither the June write-up nor this file cited DuckDB's own
documentation on the setting. Read 2026-11-16 at the 1.5 docs, the version this bench ran (Tier B for what the setting
does):

- `duckdb.org/docs/1.5/operations_manual/limits.html`, Memory use row: "Note: This limit only applies to the buffer
  manager."
- `duckdb.org/docs/1.5/guides/performance/oom.html`: "some of DuckDB's operations circumvent the database's buffer
  manager and thus they can reserve more memory than allowed by the memory limit. If this happens (e.g., DuckDB is
  killed by the operating system or an OOM reaper process), set the memory limit to just 50-60% of the total system
  memory".
- `duckdb.org/docs/1.5/guides/performance/environment.html`: "As a rule of thumb, DuckDB requires a minimum of 125 MB of
  memory per thread."
- `duckdb.org/docs/2.0/configuration/overview.html` (current release 2.0.0) adds `operator_memory_limit`, "The maximum
  memory available for query intermediates (sorts, hash tables) per connection (e.g., 256MB)". Not tested here.

So H4's mechanism (the limit bounds the buffer manager, not the process) is documented, and the 7/8 rule is tighter than
the documented 50 to 60% remedy. What this bench adds to the docs: the size of the overhead on the 1.5.3 Python client
(21.6 to 35.7 MiB above the buffer manager in capped completed trials, about 18 MiB of it the client), the failure mode
near the cap (kernel kill in 12 of 12 failing chains, 0 DuckDB OOM errors in 219 main-arm trials), H failing at both 3/4
and 1/4 so the remedy has a lower edge, spill size (up to 560.8 MiB in a completed trial), and J not fitting at any capped
point. The 64 and 128 MiB working points and the 4-thread kills at 256 MiB sit below the 125 MB-per-thread rule of thumb.
