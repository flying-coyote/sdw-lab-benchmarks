# DuckDB edge-analytics resource floor (H-EDGE-01 / §12) — 2026-06-15

The cheapest unrun book-critical bench: can a real hunting detection run under endpoint-class resource
caps, and how does it fail (graceful spill vs cliff)? A multi-step UEBA volume Z-score detection
(per-host hourly count → per-host mean/stddev → flag Z>3, the two-level aggregation) over a **10M-row**
synthetic process/flow corpus (116 MB zstd Parquet) run in DuckDB 1.5.3 under a swept `memory_limit`
(4GB→128MB) at endpoint thread counts (4, 2, 1), spill-to-disk enabled. `edge_analytics_floor.py`,
`results/edge_floor.json`. Tier B, single host.

## Result — edge-viable to 128MB / 1 core, graceful, no failures

Every one of the 18 (memory × threads) configurations **completed** (flagged the same 50 hosts), with
**zero hard failures** and graceful latency degradation:

| threads | 4GB | 1GB | 256MB | 128MB |
|--:|--:|--:|--:|--:|
| 4 | 0.42 s | 0.45 s | 0.76 s | 1.43 s |
| 2 | 0.79 s | 0.93 s | 1.05 s | 1.49 s |
| 1 | 1.06 s | 1.19 s | 1.10 s | **2.01 s** |

The hunting detection runs in **~2 s on 10M events at the tightest endpoint cap tested (128MB RAM, 1
core)** — a ~2× slowdown over a **32× memory reduction** (4GB→128MB at 1 thread). This supports H-EDGE-01:
meaningful multi-step security detection is viable under endpoint-class resources, no server required.

## Honest limitation — the working set fit, so no spill/cliff was forced

DuckDB **never spilled** (spilled_bytes = 0 at every cap), and nothing cliffed — because the UEBA
aggregation *streams*: the per-host hourly GROUP BY collapses 10M rows to a small per-host state that fits
well under 128MB, so the memory cap was never the binding constraint. So this measures **graceful operation
under caps**, not the breaking point. The actual spill/cliff floor needs a **memory-heavy detection** (a
large hash self-join or a high-cardinality `count(DISTINCT)` over a wide key that builds a hash table
exceeding the cap) — the owed extension. The transferable finding stands: the streaming hunting shape is
comfortably edge-viable; the floor for memory-bound detections (joins/distincts) is the next test.

## Cliff-finder follow-up (2026-06-15) — even a memory-heavy detection doesn't cliff at 64MB

`heavy_cliff.py` / `results/heavy_cliff.json`: the owed memory-heavy detection — a **high-cardinality
group-by on (host, usr, process, minute) over 10M rows (~10M groups)**, designed to build a hash table that
exceeds tight caps and force a spill/cliff. Swept `memory_limit` 4GB→**64MB** at threads=1:

| mem | 4GB | 1GB | 256MB | 128MB | 64MB |
|---|--:|--:|--:|--:|--:|
| result | 2.36s | 2.95s | 3.65s | 3.86s | **3.74s** |

**It completes all the way to 64MB with no failure** — and, surprisingly, **no spill files** were written to
the configured temp directory at any cap. So even the heavy ~10M-group aggregation is edge-viable at
endpoint caps (64MB/1-core, ~3.7s), and the cliff was **not reached down to 64MB**. DuckDB's out-of-core
aggregation degrades gracefully (a slight slowdown), it does not fall over. **Honest uncertainty:** a
10M-group hash "fitting" 64MB is unexpected — either DuckDB kept the aggregate under the cap efficiently, or
it handled the overflow via a mechanism that didn't write to my `temp_directory` (its memory accounting for
aggregates may not be fully governed by `memory_limit`); the *internal spill mechanism is uncharacterized*,
but the **empirical no-cliff-to-64MB result is robust**. Net: I tried to find the edge cliff with both a
streaming and a memory-heavy hunting detection and **could not force a failure down to 64MB/1-core** —
which is a stronger edge-viability result than the streaming run alone.

## Caveats (Tier B)

Single host, synthetic corpus, two detection shapes (streaming UEBA + high-card group-by). DuckDB 1.5.3.
Latency numbers are this host's; the graceful-degradation shape + edge-viability are the transferable
claims. The cliff was not reached down to 64MB even with the heavy detection (the true floor is below 64MB
or DuckDB's out-of-core operators absorb it); the internal spill mechanism at tight caps is uncharacterized
(no temp files written where configured).
