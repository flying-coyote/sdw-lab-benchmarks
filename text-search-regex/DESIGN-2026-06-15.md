The owed bench from two converging inputs: batch-2 Gemini DR #6 (BM25/full-text over lakehouses) and
the external-review P4 finding that **unstructured regex/substring over raw message fields is the
single SOC query shape most likely to invert the engine ranking** toward search engines — the regime
the SDW flagship (scan-heavy aggregation) and needle (sort-key point-lookup) benches do NOT cover.
This is the deliberately falsifiable, fair-broker test: it can go *against* the lakehouse.

## The question

On Sigma-style detection patterns (substring + wildcard + regex over a command-line text field), how
does a columnar engine compare to an inverted-index search engine — and does ClickHouse's native
full-text index + Hyperscan multi-regex close the gap the external review predicts the index wins?

Primary-verified context (external-review reconciliation): ClickHouse FTS is **token filtering, not
BM25 relevance** (no TF-IDF/positional ranking), and the Hyperscan/vectorscan multi-regex fast path
is **x86-centric**. So this bench measures token-filter + regex latency, NOT relevance ranking (a
true BM25-relevance arm is a separate, later bench).

## Arms (same corpus, same host, answer-equality checked)

- **OpenSearch 3.7.0** (the foil — inverted-index home turf): CommandLine as an analyzed `text` field;
  `match` / `match_phrase` / `regexp` queries. This is expected to win raw text filtering.
- **ClickHouse 26.5.1 brute scan** (no index): `position()/like` substring + `match()` (re2) regex
  over the String column. The "columnar without text support" baseline.
- **ClickHouse FTS** (native text index, GA v26.2+): token-filter acceleration (`hasToken`, the
  text-index path). Accelerates *tokenized terms*, not arbitrary substrings/regex — that limit is the
  point to measure.
- **ClickHouse Hyperscan multi-regex**: `multiMatchAny(CommandLine, [regex…])` — SIMD multi-pattern
  single-pass, the mechanism a columnar engine uses to fan out many Sigma regexes at once.

## Pattern set (Sigma-derived, three classes)

- **Token** (standalone terms FTS should accelerate): `powershell`, `rundll32`, `regsvr32`, `mshta`,
  `certutil`, `wmic`.
- **Substring / sub-token** (FTS token index may NOT help; brute/regex needed): `-enc`,
  `-EncodedCommand`, `FromBase64String`, `DownloadString`, `IEX`, `-nop`, `-w hidden`.
- **Regex** (Hyperscan multi-regex arm): base64 blob `[A-Za-z0-9+/]{40,}={0,2}`, encoded-flag
  variants `-e(nc(odedcommand)?)?\b`, `http[s]?://`, suspicious parent→child chains.

## Measurement

Warmup + 7 trials, median per pattern per arm; cold + warm cache both noted (per the P1 critique,
state cache discipline explicitly). Answer-equality: match counts compared across arms per pattern,
with the token-search-vs-substring semantic difference documented (a token index matches whole tokens;
`LIKE '%-enc%'` matches sub-tokens — these legitimately differ, and that difference is itself a
finding). Storage: OpenSearch index size (`_cat/indices`) vs ClickHouse `system.parts` (the index
bloat the storage-ratio claim rests on). Tier B, single host (zfr stack: OpenSearch 3.7.0 +
ClickHouse 26.5.1, both up + verified 2026-06-15). p99/tail noted where trials show spread (P1's
mean-hides-tail point for point-lookup-like queries).

## Expected outcome + why it matters either way

Per the external review, OpenSearch should win raw text filtering; CH-FTS should close the
token-filter gap; CH brute-scan should lose; Hyperscan should make multi-regex viable on the column.
If so, the result completes the **two-regime story**: columnar wins scan-heavy aggregation (flagship),
the inverted index wins text/relevance search (this bench) — and a modern columnar engine narrows the
text gap with a bolted-on token index + SIMD regex. If ClickHouse-FTS *beats* OpenSearch on token
filters, that's a stronger lakehouse claim (verify hard, it would be surprising). Either way it is a
fair-broker datapoint, not a foregone win. Routes through karen→hypothesis-validator→contradiction
before any hypothesis confidence move; candidate home is the two-regime / H3-PERFORMANCE line.
