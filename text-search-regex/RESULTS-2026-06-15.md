# text-search-regex bench — results (synthetic corpus, 2026-06-15)

The owed BM25/text-search arm (batch-2 DR#6) + external-review P4's ranking-inverting shape. Question:
does a columnar engine match an inverted-index search engine on Sigma-style text filtering, and does
ClickHouse's native full-text index + Hyperscan close the gap the index is expected to win? Tier B,
single host.

**Corpus: fully synthetic** (approved 2026-06-15 after the real-attack-telemetry hard stop — see
[[feedback_security_telemetry_injection_surface]]). 2,000,000 synthetic log messages from a random
vocabulary + planted detection targets at known rates (ground truth); no control characters, no real
attacker payloads. Loaded + queried entirely in-engine; only aggregates surfaced. **Limitation (P1
corpus-skew):** synthetic text is lower-variety than real telemetry, which flatters both the inverted
index and the token index — so treat the absolute latencies as a floor, the *cross-arm* comparison as
the signal.

Arms: OpenSearch 3.7.0 (analyzed `text` = inverted-index foil) · ClickHouse 26.5.1 brute scan
(`position`/`match`, no index) · ClickHouse native FTS (`text` index, `hasToken`) · ClickHouse
Hyperscan (`multiMatchAny`).

## Results (median of 5, count vs planted truth)

| pattern | class | truth | OpenSearch | CH brute | CH FTS | CH Hyperscan |
|---|---|---|---|---|---|---|
| powershell | token | 40240 | 6 ms ✓ | 54 ms ✓ | **5 ms ✓** | — |
| rundll32 | token | 19828 | 4 ms ✓ | 54 ms ✓ | **5 ms ✓** | — |
| B64 (sub-token) | substring | 10064 | **5 ms ✓** | 52 ms ✓ | n/a | — |
| base64 blob | regex | 7946 | **5 ms / 3159 ✗** | 107 ms ✓ | n/a | 106 ms ✓ |

Storage: ClickHouse **181 MB** vs OpenSearch **209 MB** (CH ~13% smaller on this synthetic corpus).

## Findings — text search is itself multi-modal, not "the index always wins"

1. **Token filtering: ClickHouse-FTS ties OpenSearch.** 5 ms vs 4–6 ms, both ~10× faster than CH
   brute scan (54 ms), all exact-count. The columnar engine *defends* the token-filter regime once its
   native full-text (token) index is enabled — confirming the external-review prediction (verified:
   ClickHouse FTS GA v26.2+). On token filtering the inverted index has no advantage over CH's token
   index.

2. **Substring-within-token: the inverted index wins.** OpenSearch's term-dictionary wildcard found
   the sub-token "B64" in 5 ms; CH brute scan needed 52 ms (~10×). CH's token index can't match
   sub-tokens (it would need an ngram index), so here the inverted index's term dictionary is a real
   edge.

3. **Token-spanning regex: the inverted index is fast but WRONG — the headline.** On a base64-blob
   regex (`[A-Za-z0-9+/]{40,}`), OpenSearch returned **3159 of 7946** (missed ~60%) in 5 ms, because
   the standard analyzer splits on `+`/`/` and fragments the blob into sub-tokens shorter than the
   pattern. ClickHouse's raw-text `match()` (re2) and Hyperscan `multiMatchAny` both returned the
   correct **7946** (~106 ms). So for regex over content that spans token boundaries (base64, paths,
   anything with delimiters), the index trades **correctness** for speed — it is not merely slower,
   it is *wrong* — while the columnar raw-text scan is correct. To make OpenSearch correct here you
   must regex a non-analyzed `keyword` field, which is a full-value scan (loses the index speed) — a
   correctness-vs-speed bind the columnar scan doesn't have.

## Net — extends the two-regime story

"Text search" is not one regime. **Token filtering** is a tie (CH-FTS = inverted index); **substring**
favors the inverted index's term dictionary; **token-spanning regex** favors the columnar raw-text
engine on *correctness* (the index silently undercounts). So the inverted index is the home turf only
for token/substring filtering — and even there the columnar engine now matches it on tokens with FTS.
The security-relevant kicker: **base64-payload hunting via an inverted index can silently miss the
majority** (3159/7946 here) due to analyzer tokenization, which is a detection-*fidelity* argument for
the open columnar engine, not just a cost argument. Hyperscan matched `match()` here because only one
regex was tested; its real advantage is fanning out *many* Sigma regexes in one pass — untested with a
single pattern, owed as a follow-up. Storage was only ~13% apart on synthetic data; the external
review's real-data figure (ClickHouse ~5× smaller than Elasticsearch on 50B OTEL logs, vendor Tier-C)
suggests the gap widens on high-entropy real telemetry.

Gate before any hypothesis confidence move (karen → hypothesis-validator → contradiction). Candidate
home: the two-regime / engine-specialization frame (text search as a third axis, itself split into
token/substring/regex sub-regimes). Caveats: synthetic corpus (flatters indexes), single-regex
Hyperscan, OpenSearch analyzed-text defaults (a custom analyzer or `wildcard` field type would change
the substring/regex behavior — the defaults are what most SIEM deployments run).
