# Multi-user concurrency — single-host saturation (2026-06-15)

## What this closes (and what it does not)

The flagship two-regime result measures **one query at a time** (single user). The thesis names
the honest open extension itself: *does the single-query advantage survive when many analysts query
at once?* This bench closes the single-**USER** → multi-**USER** question on a single host. It does
**not** test single-host → distributed/cluster scaling (still one host, one engine process, one
OpenSearch shard) — that horizontal-scale extension stays open.

Safety boundary honored: structured-data only, aggregate output (top-10 source IPs by bytes). No raw
event rows enter the harness ([[feedback_security_telemetry_injection_surface]]).

## Method

- **Workload:** the flagship top-talkers scan-aggregation, identical across engines —
  `SELECT orig_h, SUM(orig_bytes + resp_bytes) AS b FROM soc.conn GROUP BY orig_h ORDER BY b DESC LIMIT 10`
  on `soc.conn` (10.3M rows). The OpenSearch foil runs the equivalent `terms` aggregation on `orig_h`
  ordered by a painless `sum` of the two byte fields, over the `zeek_conn` index (10M docs, 1 shard).
- **Closed-loop concurrency:** N ∈ {1, 2, 4, 8, 16, 32} identical clients, each modeling one
  interactive analyst (issue query → wait for full result → immediately issue the next). Each level
  runs a 20 s timed window after a warmup; latency recorded per completed query; QPS = completed / window.
- **Resource safety:** one engine under load at a time (others idle), `MemAvailable` abort-guard at
  1.5 GB (never tripped; min free stayed ≥19 GB). Single host (Beelink 5800H, WSL2, 14 cores).
- **Cache fairness:** warm page cache for all; ClickHouse `use_query_cache=0`; the other SQL engines
  have no result cache; the OpenSearch foil runs with `request_cache=false` so it **recomputes** the
  aggregation each query (otherwise the shard request-cache memoizes the identical agg and reports a
  false ~3 ms — caught in smoke testing). All four non-Dremio arms therefore do the real compute every query.
- The four Iceberg engines ran inside `ejs-lab` (internal network reaches Nessie/MinIO); the foil ran
  from the host against `:9200`. Reuses `soc-query-shapes/ejs_clients.py`. Harness:
  `concurrency_bench.py`; raw `results/conc_<engine>.json`.

## Findings

1. **The columnar Iceberg engines have almost no concurrency headroom** (1.1–1.3×). A single heavy
   scan-aggregation already spreads across all 14 cores, so added concurrent users get no extra
   throughput — QPS plateaus at N=1 and p50 grows roughly linearly with N (ClickHouse 159 ms → 5,439 ms
   from N=1 to N=32). They front-load parallelism *into each query*.

2. **The foil scales the opposite way** — 6.7× from N=1 to N=16. A single-shard OpenSearch agg is light
   on per-query CPU, so it has spare capacity to run concurrent queries until it hits core saturation
   around N=16. It parallelizes *across users*, not within a query.

3. **Both converge to the single-host CPU ceiling (~6–7 QPS).** The columnar engines arrive there at
   N=1; the foil climbs to it by N=16. Total host CPU is the ceiling either way — the engines just
   spend it differently.

4. **The single-query latency advantage is a low-concurrency phenomenon.** At N=1 ClickHouse-Iceberg
   beats the foil ~6× on p50 (159 ms vs 973 ms); by **N=16 the foil's p50 (2,667 ms) ties
   ClickHouse-Iceberg (2,684 ms) and StarRocks (2,664 ms)**, and all three sit at ~6.3 QPS. The
   latency edge fully erodes into a throughput tie once enough analysts query at once on one host.

5. **StarRocks is the best-behaved under concurrency** — highest QPS ceiling (6.79) and the tightest
   tail (p95/p50 ≈ 1.16 at N=16, vs ClickHouse 1.30, Trino 1.90). Its MPP scheduler degrades more
   gracefully than ClickHouse's all-cores-per-query model. This complements the UEBA two-level-agg
   finding where StarRocks overtook ClickHouse — engine specialization shows up again, now under load.
   Trino carries a low ceiling and large tail blow-ups (the Dremio arm is withheld under its
   benchmark-publication terms).

## Caveats (Tier B, single host)

- **Edition-bound — the most important caveat.** These are the **OSS / community editions**:
  ClickHouse-server OSS, StarRocks allin1 (OSS), Trino OSS, **Dremio OSS Community**, OpenSearch
  (Apache). Several engines sell *concurrency / workload-isolation* as a paid-edition feature, so the
  "no concurrency headroom" finding may be partly an edition artifact, not an engine property —
  most plausibly for **Dremio** (Enterprise **Elastic Engines** give per-workload engine isolation, the
  exact mechanism for concurrency; the OSS Dremio concurrency result (withheld) is the likeliest
  edition-limited case) and **Trino** (Starburst Enterprise/Galaxy resource management + Warp Speed
  caching), and secondarily **StarRocks** (CelerData shared-data). ClickHouse and OpenSearch concurrency
  are governed by configuration, not license, so their curves are edition-fair. Scope the cross-engine
  reading to OSS editions; enterprise concurrency features are **untested** and a named open extension
  (SDW is pursuing temp vendor lab licenses to test them independently — fair-broker).
- One query shape (a heavy scan-aggregation — the regime where the lakehouse wins single-user). A
  point-lookup or text shape would scale differently; this is the hunting-aggregation case.
- Single OpenSearch shard. More shards would parallelize a single query (changing the N=1 number) and
  shift the concurrency curve — this is a small-deployment foil, labeled as such.
- Closed-loop (each client waits for its result), not open-loop fixed-arrival. Warm cache. Absolute
  ms differ from the flagship single-query draw (warm cache + `request_cache=false` + this exact shape)
  — this bench measures the *shape of scaling under concurrency*, not a re-draw of the flagship ratio.
- Single host only — the distributed/cluster extension that would add horizontal throughput is **not**
  tested here and remains the honest open question.

## What it means for the thesis

The flagship per-query wins (10× scan-aggregation, the open-format tax) are real and reproducible, but
they are a **latency** advantage at low concurrency, not a **throughput** advantage at high concurrency
on a single host. With many concurrent analysts the columnar engine's edge erodes toward the host CPU
ceiling, and at that point the answer to "is the lakehouse faster?" becomes "for latency with a few
power users, yes; for throughput with a crowd on one box, it converges — and you reach for horizontal
scale." That is exactly the "where YOUR stack breaks" honesty the fair-broker posture wants, and it
bounds H3-PERFORMANCE-01 rather than inflating it.
