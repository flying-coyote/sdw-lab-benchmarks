# #25 mv-rewrite-freshness — results (2026-06-15)

The pre-registered bench compared two transparent-rewrite accelerators at matched freshness on a
live Iceberg table: **Dremio Reflections** vs **StarRocks async MV**. Tier B, single host (ejs
stack: Dremio OSS 26.0, StarRocks 4.1, iceberg external catalog over Nessie/MinIO, the SOC `conn`
10M-row Zeek table).

## The matched-freshness COMPARISON cannot run — the Dremio arm is blocked

Dremio Reflections do not persist over an Iceberg table managed by an external Nessie catalog, via
either read path (see `DREMIO-ARM-FINDING-2026-06-15.md`): the Nessie-versioned source materializes
a reflection that expires at `available_until`=epoch 0, and the untried raw-S3-source fix fails to
promote the table ("Failed to get iceberg metadata" — catalog-managed metadata, no version hint).
So the head-to-head matched-freshness comparison the bench was designed for is not runnable on the
open Nessie/Iceberg substrate with Dremio-26. That is the bench's primary finding: the two-engine
comparison is blocked by Dremio's integration limit, not a measurement.

## StarRocks async-MV half (the achievable single-engine result)

`starrocks_freshness.py` characterizes the StarRocks async MV's freshness/acceleration on a moving
table (one async MV, per-`resp_p` scan-aggregate, `REFRESH ASYNC EVERY (INTERVAL 60 SECOND)` — 60 s
is StarRocks' enforced `materialized_view_min_refresh_interval`):

- **Acceleration: 2.0×** on this scan-aggregate (MV 12.0 ms vs base Iceberg scan 24.2 ms, warm
  median of 7). Modest because the base aggregate is already ~24 ms on 10M rows in StarRocks; the
  MV only pre-sums the per-`resp_p` counts. Heavier shapes accelerate far more — the #23 P5 arm's
  pre-built MVs over joins / `COUNT(DISTINCT)` show larger gaps — but P5 also found the MV buys **no
  interference-knee headroom** (at saturation the bottleneck is the scheduler/coordinator, not the
  per-query compute the MV removes), so "the MV makes the query faster" and "the MV helps under
  load" are different claims.
- **Freshness: caught up ~12 s after a 300k-row append** (lag went 300k → 0 by t=12.4 s), well
  inside the 60 s minimum refresh interval. So the staleness budget is bounded by the refresh
  interval (≤60 s here, the engine floor) and in this run the auto-refresh closed the gap much
  faster. Single append / single catch-up — a band would need repetition; the bound (≤ refresh
  interval) is the structural claim.

## Net

The bench's intended contribution (which accelerator gives the better freshness↔acceleration
tradeoff) cannot be delivered — Dremio's arm is blocked on the open catalog path. What stands: the
**Dremio-Reflections-don't-work-over-open-Nessie/Iceberg** finding (version-bound, Dremio OSS 26.0),
and a single-engine StarRocks characterization (2.0× on a light aggregate, staleness ≤ the 60 s
refresh floor). A real head-to-head would need a Dremio-native catalog (Arctic / Hadoop-tables with
a version hint) — i.e. NOT the open substrate the rest of the lab standardizes on — so it is parked
unless the substrate changes. Re-check Dremio's Nessie/Reflections support on a newer release.
