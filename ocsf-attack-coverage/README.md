# OCSF ATT&CK coverage: per-technique Sigma firing over the planted testbed

## What it measures

This bench turns the `ocsf-sigma-detection` round trip into a per-technique coverage table. Eight ATT&CK
techniques are listed in [technique_ocsf_map.json](technique_ocsf_map.json), each bound to an OCSF class
and a Store F table, and every technique lands in one of three states: DETECTED (the planted event is in
the rule's matches and precision is at least the stated floor T = 0.9), NOISY (the planted event is
matched but precision is below T), or MISSED. For each MISSED technique the runner asks the Security
Context Graph (`../security-context-graph/`, through the dependency-free port in
[scg_coverage.py](scg_coverage.py)) which D3FEND defenses *may* counter it and how many of those survive a
`min_trust` of 0.6, and it records those as leads rather than as coverage. The corpus is a ground-truth
tagged projection of the testbed's Store F ([gen_corpus.py](gen_corpus.py)); no new rows are generated.

## Result (Tier B)

`results/coverage.json` records 3 of 8 DETECTED, 1 NOISY and 4 MISSED, with 0 of the 74 D3FEND
may-counter leads for the four MISSED techniques surviving `min_trust` 0.6. The eight rows split into two
kinds, and only one kind is a measurement:

| kind | techniques | what the row is |
|---|---|---|
| inherits the planted-value rules | T1059.001 DETECTED, T1098 DETECTED, T1071 DETECTED, T1021 NOISY (precision 0.0003, 2,959 benign port-3389 matches) | the four rules in `rules/` are byte-identical to `../ocsf-sigma-detection/rules/` and run over the same Store F, so these four states follow from the planted values those rules key on (see that bench's README); they show the round trip and are not a recall |
| inventory ("no rule or no needle") | T1003.001, T1048, T1110, T1490, all MISSED | no rule ran for any of them, so MISSED here is a count of what the harness lacks and not a detection that fired and failed |

Within the inventory rows the reasons differ. T1003.001 and T1490 have no rule and no event planted in
the testbed. T1110 has a correlation rule in `rules/correlation/brute_force.yml` that this bench does not
score. *(corrected 2026-11-17)* T1048 does have planted positives: the testbed's 30 exfiltration events
are tagged T1048 in the API Activity table (`gen_corpus.py:50-51`; `corpus/_corpus_manifest.json` lists
T1048 among the `api` table's tags), but `technique_ocsf_map.json` binds T1048 to Network Activity (4001)
with no rule, so the row is "planted, no rule" rather than "no positive to catch" as
`results/RESULTS.md` puts it.

## What would have made it fail

For the four rule-bearing rows, nothing on this corpus, for the reasons in the sigma-detection README. For
the four inventory rows there was nothing to fail, because nothing ran. The part of this bench that could
have come out otherwise is the D3FEND lead count: the SCG coverage call could have returned leads that
clear `min_trust` 0.6, and on this run none did. The mixed-case check below is the one test in the folder
that was built to break a rule, and it did break one.

## Pre-registration

None. No file in the folder records a design frozen before the run.

## Reproduce

```bash
python ocsf-semantic-testbed/generate.py          # the shared corpus
python bench-a-context-collapse/run.py            # builds Store F
python security-context-graph/scg.py              # the graph the gap hop reads
python ocsf-attack-coverage/gen_corpus.py         # tagged projection of Store F into corpus/
python ocsf-attack-coverage/run.py                # writes results/coverage.json + RESULTS.md
```

`run.py --smoke` writes `results/coverage.smoke.json` instead. As the 2026-11-16 mixed-case check
records, pySigma-backend-sqlite 2.x emits `FROM logs` and `run.py:89` replaces only the older
`<TABLE_NAME>` placeholder, so with today's unpinned install every rule errors and scores MISSED; install
the older backend the June run used to reproduce the committed numbers.

## Results

- [results/RESULTS.md](results/RESULTS.md) and [results/coverage.json](results/coverage.json): the entry point (regenerated by `run.py`).
- [RESULTS-MIXED-CASE-2026-11-16.md](RESULTS-MIXED-CASE-2026-11-16.md) with `results/mixed-case-check-2026-11-16.json`: post-hoc, not pre-registered. It compiles each of the four rules and runs it on SQLite and DuckDB over five planted rows. It agrees with `results/RESULTS.md` (it does not touch the corpus or the committed states) and adds two findings: the `contains` rule loses every case variant on DuckDB, and the two string-equality rules are case-sensitive on both engines where Sigma's default is case-insensitive.

## Versions and pins

`requirements.txt` pins `duckdb==1.5.3` and leaves `pysigma` and `pysigma-backend-sqlite` unpinned, with
a dated comment explaining that the June versions were not recorded. The mixed-case check used pySigma
2.0.3, pySigma-backend-sqlite 2.1.1, DuckDB 1.5.3 and SQLite 3.45.1.

## Evidence tier and limits

Tier B, one synthetic chain on one machine. The transferable part is the three-state split and the
refusal to count a may-counter lead as coverage; the counts are bounded by what the testbed plants and by
which techniques the map gives a rule.
