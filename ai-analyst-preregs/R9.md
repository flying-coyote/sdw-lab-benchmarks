# R9 pre-registration: second planting run against the 27 zero-defense techniques

Frozen by agent before any run; not owner-reviewed. Nothing here has been executed beyond the instrument
inventory listed under "Inventory done before freeze". The sha256 at freeze is in `README.md`. Source
request: `SITE-REVIEW-2026-11-09.md` section 5, row R9, and the closing paragraph of the 27 section on
`/research/measuring-the-27-zero-defense` (`~/securitydataworks/src/pages/research/measuring-the-27-zero-defense.astro`),
which names a second run planting inter-process-communication and file-hiding members as the next step.

This area needs no paid model calls: the harness is deterministic (pySigma-compiled rules over DuckDB, no
LLM in the loop, so the §10 LLM-arm rules do not apply and the deterministic-arm exemption is stated here).
It is held back because it is a longer build (a generator extension and new field mappings), not because of
spend.

## Question

The D3FEND wall (v1.4.0, unchanged on v1.6.0 per the page's 2026-11-03 note) leaves 27 ATT&CK techniques
with no artifact any remaining defense watches. Does that structural zero in the defensive knowledge graph
correspond to a measured zero in detection, when the techniques are planted into OCSF telemetry and
unmodified SigmaHQ rules are run over it with the same harness and scoring rule as the first run?

## Instrument

- **Harness**: `ocsf-attack-coverage` unchanged in scoring: DETECTED (needle in matched set, precision at or
  above T = 0.9), NOISY (needle matched, precision below T), MISSED (needle not matched, or no rule, or no
  needle). The miss reason is extended to five values so the states stay comparable with run 1:
  `rule_no_fire`, `no_rule`, `no_needle`, `no_observable_table`, `no_observable_in_corpus_os`.
- **Rule selection, fixed now**: every rule in the pinned commit's `rules/` directory whose tags include the
  technique ID and whose logsource maps to a table present in the store, compiled unmodified through
  pySigma to SQL. No rule is edited or tuned. The resolved rule list with rule IDs is an output of the run.
- **Needles**: one planted malicious event (or event set) per plantable technique, written by a seeded
  extension of the testbed generator (seed 20261109, distinct from the corpus seed 20260601 so the existing
  corpus fingerprint is unchanged).
- **Benign confounders**: 50 lab-authored benign lookalikes per plantable technique (for example installer
  `attrib +h`, benign stream writes, files with legitimate multi-dot names). These make the precision column
  meaningful, and they are a declared limit, because precision depends on what I chose to plant as benign.
- **Real-data stratum**: the same selected rules run over the APT29 day-1 raw store
  (`ocsf-context-collapse-apt29/_work/raw`, which does carry file_event and registry_event). The only gold
  there is the known right-to-left-override dropper (`ocsf-airgap-agent/results/RESULTS.md`); other matches
  are reported as matches, not as true or false positives, unless they correspond to a step in the published
  ATT&CK Evaluations APT29 emulation mapping.

## Hypotheses and what would prove each wrong

- **H1, structural zero is not a detection zero.** At least 3 of the 5 process-class plantable members reach
  DETECTED at T = 0.9 with an unmodified SigmaHQ rule. Wrong if fewer than 3 do. If H1 holds, the hole the
  wall shows is in the D3FEND graph and not in public detection content, which is the reading the page
  already gives in prose and would then have a measurement behind it. NOISY counts as a distinct outcome,
  not a pass.
- **H2, the IPC family stays dark.** None of T1559, T1559.001 and T1559.002 reaches DETECTED in the
  testbed run. Wrong if any of them does.
- **H3, Phase 0 control.** T1003.001 and T1490 reach DETECTED once needles are planted. Wrong if either stays
  MISSED or lands NOISY; that outcome would be reported as a runtime miss and would lower trust in the
  harness's handling of the 27 until explained.
- **H4, real-data RLO.** At least one T1036.002-tagged process_creation rule matches the APT29 day-1 dropper.
  Wrong if none does.

## Run count and determinism

Deterministic, so there is no CV to report; methodology §9 applies instead:

- Three reruns per configuration, asserting `rerun_identical = true` on `coverage.json` (sorted sets of
  event uids).
- Two background scales (1x and 10x benign volume), because a finding seen at one scale may not reproduce
  at another (the chDB lesson).
- The planted corpus is pinned with `lib.common.pin_artifact()` (logical fingerprint, structural manifest),
  not just the generator.

## Cost estimate

- **USD: $0.** No model calls, no cloud.
- **Compute**: under 1 hour total, including reruns and both scales (run 1's harness scores over about 177k

- **Build hours**: Phase 0 rescoring including correlation-rule set scoring, about 3 to 4 hours; needle and
  confounder generator for the 7 dns/network/process members, about 6 to 8 hours; optional registry and

  about 3 hours. **About 12 to 15 hours without the extension, 20 to 27 with it.**

## Stop rule

The run is complete when every one of the 11 targets and the 4 Phase 0 techniques has a state and a miss
reason, at both scales, with three identical reruns. If the extension is not built within the build budget,
the dependent techniques are reported as `no_observable_table` and the run still publishes.

## Limits declared up front

- The needles and benign confounders are lab-authored; a technique DETECTED here is detected against my
  planting, which sizes a method and does not certify a deployment (Tier B, synthetic, one machine).
- The zero-defense status is a fact about D3FEND's mapping at v1.4.0 and v1.6.0, not about field
  defendability; the page already says this and the run does not change it.
- Only SigmaHQ `rules/` at one commit is in scope; vendor content and the emerging-threats directory are
  not, so a MISSED(no_rule) here says nothing about commercial rule packs.
- The macOS members cannot be tested against a Windows corpus at all.
