# Two-regime generalization on EDR/Sysmon — it SHARPENS the claim (2026-06-15)

#68: does the flagship two-regime split (columnar/lakehouse wins hunting aggregations; inverted index
wins selective lookups + text) generalize beyond Zeek conn to a structurally different log shape? Tested
on a synthetic EDR/Sysmon process-creation stream (3M rows: image/parent_image/command_line+md5-tail/
process_guid/sha256/integrity_level — wide, high-entropy, text-y) loaded into ClickHouse (MergeTree,
columnar arm) and OpenSearch (force-merged single segment, index arm), host-run. `edr_two_regime.py`,
`results/edr_two_regime.json`. Tier B, single host, 3M rows.

## Result

| query | regime | ClickHouse (columnar) | OpenSearch (index) | winner | answer-equal |
|---|---|--:|--:|---|---|
| top hosts (terms agg) | agg | 15.2 ms | 5.4 ms | index 2.8× | — |
| distinct users / image (high-card) | agg | 91.4 ms | 93.7 ms | tie (1.0×) | — |
| integrity-level histogram (terms agg) | agg | 11.7 ms | 2.3 ms | index 5.1× | — |
| process_guid exact lookup | lookup | 3.8 ms | 2.0 ms | index 1.9× | 1 == 1 ✓ |
| command_line **text** search | lookup | 55.5 ms | 1.6 ms | **index 34.7×** | 375,264 == 375,264 ✓ |

**The two-regime split does NOT hold as stated on EDR at this scale — the index wins or ties all five.**

## What it actually says (honest, two-sided)

**The index-wins-lookups-and-text half GENERALIZES — decisively.** OpenSearch wins both lookups, and the
**command_line text search 34.7×** is the cleanest result in the set: full-text on an analyzed field is the
inverted index's home turf, where ClickHouse must scan-and-`position()` every row. Both lookups are
**answer-equal** (1==1 on the GUID, 375,264==375,264 on the text match) — manageability/regime aside,
correctness holds. This completes the two-regime *symmetry* the backlog flagged as owed (the index's home
turf), on a second log shape.

**The columnar-wins-aggregations half does NOT generalize to cheap terms-aggregations at small scale.** The
index won the two terms-aggregations (top-hosts 2.8×, integrity histogram 5.1×) and only *tied* the
high-cardinality distinct-count — because OpenSearch serves low-cardinality terms aggregations from
doc-values cheaply, and at 3M rows on a force-merged segment there is little for a columnar scan to win.
**This sharpens the two-regime claim:** the lakehouse/columnar advantage is specific to **heavy
scan-aggregations at scale** (the flagship's 10M-row computed-SUM hunting aggregations, where it measured
5.4–46.8×), *not* "aggregations" in general — cheap terms-counts on a few million rows are the index's
territory too.

**Honest confound (gate condition).** The aggregation queries here were *cheap terms-aggs* (top-N keyword
counts), which are exactly OpenSearch's doc-value strength — not the flagship's heavy computed scan-aggregation
shape. So "two-regime doesn't hold on EDR" is partly a **query-shape choice**, not purely a scale/log-shape
law. The robust, transferable findings are: (a) index wins selective lookups + text decisively and that
generalizes; (b) the columnar aggregation advantage is heavy-scan-at-scale-specific, not universal; (c)
answer-equality holds across engines on the lookups. The owed fair test of the columnar half on this corpus
is the flagship's **heavy scan-aggregation shape at 10M EDR rows** — not run here.

## Consequence

For the fair-broker posture this is a *strengthening*: it disciplines the two-regime claim against
over-reading "the lakehouse wins aggregations." The accurate statement is **"the index wins selective
lookups and text search (always, decisively on text); the columnar lakehouse wins heavy scan-aggregations
at scale"** — and on a small EDR corpus of cheap aggregations + lookups, the index dominates. The text-search
34.7× is a clean addition to the "where the SIEM/index wins" evidence (we test where the incumbent wins, not
only where the lakehouse wins).

## Heavy-scan fair-test at 10M (2026-06-15) — RESOLVES the confound: the columnar half DOES generalize

The owed complement ran (`edr_heavy_scan_agg.py` / `results/edr_heavy_scan_agg.json`): the same EDR/Sysmon
corpus at **10M rows** with a numeric measure (`bytes_sent/bytes_recv`) added, the flagship's **heavy
scan-aggregation** shape instead of cheap terms-aggs, ClickHouse vs OpenSearch.

| query | regime | ClickHouse | OpenSearch | winner |
|---|---|--:|--:|---|
| top hosts by SUM(bytes_sent+recv) | heavy_agg | 75.5 ms | 646.4 ms | **columnar 8.6×** |
| high-card SUM by subject_user (~20k) | heavy_agg | 115.7 ms | 545.7 ms | **columnar 4.7×** |
| avg(length(command_line)) by image (computed) | heavy_agg | 61.9 ms | 22,087 ms | **columnar 356.8×** |
| command_line text search (control) | lookup | 173.1 ms | 1.2 ms | index 144× |

**Columnar wins 3/3 heavy aggregations; the index keeps the text lookup.** This resolves the first EDR run's
confound: that run's "two-regime doesn't hold on EDR" was a **query-shape artifact** — its cheap terms-aggs
(top-N keyword counts) are served from OpenSearch doc-values, where the index is fast. With the flagship's
**heavy scan-aggregations at scale**, the columnar half holds decisively on EDR too: **4.7–8.6× on the fair
numeric-SUM aggregations** (both engines have doc-values on the numeric fields; ClickHouse still wins the
scan-and-hash at 10M), and an extreme **356×** on the computed avg-command-line-length — the latter is partly
*structural* (a `text` field has no doc-value, so OpenSearch must script over `_source`), so lead with the
4.7–8.6× numeric result as the fair heavy-agg figure and cite the 356× as the computed-over-text extreme.

**Reconciled boundary (the sharpened two-regime):** taking the 3M cheap-terms run + this 10M heavy run
together, the split is precisely **"columnar wins HEAVY scan-and-compute aggregations; the inverted index
wins selective lookups, text search, AND cheap doc-value terms-counts."** The discriminator is the
**weight/shape of the aggregation** (full scan + per-row compute + high-cardinality hash vs a cheap
pre-indexed terms-count), not "aggregations vs lookups" in the abstract. The flagship's Zeek two-regime
generalizes to EDR/Sysmon on the matching query shapes.

## BM25 relevance (2026-06-15) — completes the index-side symmetry: a CAPABILITY gap, not just latency

`bm25_relevance.py` / `results/bm25_relevance.json`, reusing the loaded 10M `edr_heavy` (OpenSearch
command_line = analyzed `text`; ClickHouse command_line = plain String). The earlier EDR text leg showed the
index wins token *matching* (34.7×); this shows the deeper point — relevance *ranking*:

| query | OpenSearch BM25 | ClickHouse | gap |
|---|--:|--:|--:|
| "powershell -enc whoami" | 23.6 ms (ranked, TF-IDF) | 274.9 ms (full-scan TF count) | ~11.6× |
| "process call create" | 17.7 ms (ranked) | 303.9 ms | ~17.2× |
| "schtasks netsvcs query" | 20.6 ms (ranked) | 248.9 ms | ~12.1× |

**OpenSearch ranks by BM25 (TF-IDF) natively** via the inverted index (~18–24 ms); **ClickHouse has no native
relevance ranking** — it matches via full scan (249–304 ms, ~12–17× slower) and any "rank" is a hand-rolled
term-count *without IDF*. So the index's two-regime win on text includes a **capability gap** (relevance
ranking is first-class for the inverted index, absent in the columnar engine), not only a latency gap — which
completes the two-regime symmetry: the SIEM/index's home turf is selective lookups, token matching, **and**
relevance ranking. **Honest caveat:** the synthetic command_lines are templated, so BM25 score variance is
low (uniform 1.05 / 2.66) — the *ranking-quality* discrimination is under-demonstrated (real logs have richer
text → more BM25 separation); the **capability gap (no native BM25 in CH) and the ~12–17× latency** are the
transferable findings.

## Caveats (Tier B)

Single host, synthetic EDR corpus, force-merged single-segment OpenSearch with request_cache off. The first
run is 3M (cheap terms-aggs, index-favorable by query choice); the fair heavy-scan run is 10M with the
flagship's aggregation shape (columnar-favorable on genuine scan-aggregations). The 356× computed-over-text
figure is structural (text has no doc-value) — the fair heavy-agg number is the 4.7–8.6× numeric SUM. The
columnar advantage grows with scan size; both numbers are this host's, the per-shape ordering transfers.
BM25: templated text limits ranking-quality demo; capability + ~12–17× latency are the robust findings.
