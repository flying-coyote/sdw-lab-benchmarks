# R6 — planning cost vs fragmentation: Iceberg manifests vs DuckLake SQL catalog

See the docstring in [`run.py`](run.py) for the design: same DuckDB engine reads both
formats as the table fragments into more files, isolating how each format's metadata
layer resolves "which files must I scan."

## Hypothesis mapping

Advances **H-DUCKLAKE-02**: the planning-cost scaling shape (manifest traversal vs SQL

hypothesis tracks. *(ID recorded 2026-06-10 per the benchmark-alignment audit.)*

## Layout and audit notes (added 2026-11-17)

### What it measures

5,000,000 rows written to Iceberg and to DuckLake over 10, 50 and 200 commits, each commit one data file, then read end to end by the same DuckDB engine, so the variable is how each format's metadata finds the files to scan. Each format's own planning step (pyiceberg `plan_files()` and DuckLake's catalog query) is timed alongside.

### Result, and whether it is measured

Measured, with identical answers from both formats. From 10 to 200 files, end-to-end latency grows 6.53× on Iceberg and 1.43× on DuckLake, and the planning step grows 17.6× and 1.21× (`results/results.json`). The two planning mechanisms are different code, so their absolute milliseconds are not comparable; the growth shapes are the result.

### What would have made it fail

DuckLake's catalog query could have grown with file count as Iceberg's manifest walk does; it did not. Medians carry CVs of 1% to 12%.
