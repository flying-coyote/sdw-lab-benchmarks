# STREAM-COMPLEXITY v2 — results (2026-11-03)

Batch vs Kafka+Flink vs Feldera OSS (plus a containerised batch arm) for one identical detection outcome. Binding plan: `../PRE-REG-stream-complexity-v2-2026-11-03.md`, frozen in lab commit `177934e` before any scored run; it was not edited during or after the run, and every place where the run could not follow it as written is a dated note in the Deviations section. Target hypotheses: H-IMPL-01 (Streaming Architecture Hidden Costs, 1/5; magnitude D, direction B per the 11-03 adjudication) and, adjacently, H-STREAMING-02. Run by an agent session on 2026-11-03; scored by the same session, so the pre-registration is the main protection against the author's interest, as it was in July. **The F arm is EDITION-BOUND throughout: Feldera open-source edition v0.375.0, where checkpointing and fault tolerance are Enterprise-only and were not tested. Tier B.**

## Honesty boundaries (carried verbatim from the pre-registration)

Single host, Docker Desktop/WSL2, synthetic seeded corpus (injection-surface boundary: no real telemetry), ONE detection shape, single-node every arm. Kafka 4.3.1 + Flink 2.2.1 as the canonical streaming stack and Feldera open-source edition (pinned tag) as the incremental-view-maintenance arm; EDITION-BOUND, since checkpointing and fault tolerance are Enterprise-only and were not tested. Complexity and dependence proxies are not dollars, headcount, or on-call burden, so this measures the operational-surface direction of H-IMPL-01 and the gated-feature half of the platform-dependence refinement, not cost. Assumptions under test: the canonical streaming stack carries structurally more operational surface than an equivalent-outcome batch path, and an incremental engine that removes that surface does so partly by relying on vendor-gated features.

Redundancy limit (harness fix 5, stated as the pre-reg requires): Kafka ran as one KRaft broker, Flink as one jobmanager and one taskmanager, Feldera as one OSS pipeline-manager, batch as one process, BC as one container. No arm had a peer to fail over to, so nothing here measures replication, leader election, ISR catch-up, HA jobmanager or multi-host recovery, and the hypothesis's "higher infrastructure redundancy" clause gets no evidence from this bench in either direction.

## What ran

- **Detection and corpus**: unchanged from July. "≥5 failed logins per (user, src_ip) within a 60-second epoch-aligned event-time tumbling window", seed 20260719, 500,000 events, 30 ground-truth alerts from the independent reference implementation in `gen_corpus.py`.
- **B (batch, July arm, unchanged)**: `batch/land_microbatches.py` + `batch/batch_job.py` (bare host Python process, DuckDB 1.5.3).
- **S (streaming, July arm, unchanged)**: `apache/kafka:4.3.1` + `smx-flink-kafka:2.2.1` (Flink 2.2.1, connector 5.0.0-2.2), July compose, SQL job and sink consumer.
- **F (Feldera OSS, new)**: one `pipeline-manager` container, `images.feldera.com/feldera/pipeline-manager:0.375.0@sha256:3dae7d82…e9ae0fc` (index digest, identical on `images.feldera.com` and `ghcr.io`, checked 2026-11-03; `/v0/config` reports `"edition":"Open source","version":"0.375.0"`). Files: `feldera/docker-compose.yml`, `feldera/detection.sql` (an `append_only` table, a local view deriving `event_time`, `LATENESS … INTERVAL 2 SECONDS`, and an `emit_final` view over `TUMBLE`), `feldera/deploy_pipeline.sh`. Input by HTTP ingress from `feldera/replay_http.py` (July pacing, shared replay clock); output from the view's HTTP egress via `feldera/drain_alerts.py`. **`emit_final` primary worked; the fallback was not needed** (0 delete records across every trial and fault).
- **BC (containerised batch, new)**: the same `batch/batch_job.py`, in one container built from `python:3.12-slim@sha256:090ba77e…dfe203` with DuckDB 1.5.3 / pyarrow 24.0.0, `restart: on-failure` (`bc/Dockerfile.batch`, `bc/docker-compose.yml`).
- **Clean trials**: three at 20× and one at 1× (event time = wall time), all four arms concurrently on one shared replay clock, 10-second moving-parts sampler throughout (`v2/run_trial_v2.sh`, `v2/sampler.py`).
- **Fault battery**: S1, S2, B1, B2, B3, F1, F2 as frozen, plus BC1 from the BC predictions, each on the full corpus at 20×, kill at event-time minute 45 (replay start + 135 s), held outage 30 wall-seconds, then the recover script and a post-recovery answer-equality check over the full corpus (`v2/faults_v2.py`, `faults/recover_*.sh`). Two exploratory faults outside the pre-registration (B2x, B3x) are reported separately and score nothing.
- **Smoke before scoring**: one 100× four-arm trial (gate PASS) and one full smoke pass of every fault, which confirmed for each that the arm's output file exists and grows after recovery. The smoke pass also found three harness bugs in the F fault scripts, all fixed and re-smoked before the scored F faults ran (Deviations 7–9).

Per-arm step totals across the frozen faults: **B 3** (1 + 0 + 2), **S 4** (2 + 2), **F 7** (4 + 3, EDITION-BOUND), **BC 1**.

The headline from July's harness flaw is gone: every arm's output file existed and kept growing after recovery, and every arm got back to the full 30/30 answer with no missing and no extra alerts once its frozen rewind rule had been followed. What separates the arms is the work and the waiting, so the details are worth reading row by row.

- **S1** needed no job restart (0 `RUNNING → RESTARTING` transitions in the jobmanager log), and the July producer's librdkafka client simply held and retried the unacknowledged events until the broker returned (0 delivery errors). The broker was answering again 17 s into recovery, but the first new alert took 91 s from the kill, roughly 43 s after the broker was back, which looks like Kafka-client reconnect backoff in the Flink source and sink rather than anything the operator could do.
- **S2** restored from checkpoint 14 (`Recovering subtask 0 to checkpoint 14`) with one job restart, and re-emitted one alert it had already written, the non-transactional-sink duplicate the pre-reg expected; the sink adapter's dedup kept it out of the file.
- **B1** is still the instant single restart July measured.
- **B3** is where batch paid: the bare job has no supervisor, so a reader-visible half-written file killed it (`InvalidInputException: No magic bytes found at end of file`), and the operator had to wait for a readable file and restart it.
- **F1 and F2 (EDITION-BOUND)** came back with no recompile (program status `Success` throughout, compiled binary reused), but on both faults the OSS manager left the pipeline `Stopped` with `RunnerCheckError` and the operator had to start it, compute the rewind point from the replayer's `last_acked`, and re-send from the start of the oldest open window (base + 2,760 s on both runs). The first failed send landed at base + 2,770 s (F1) and base + 2,778 s (F2), so the kill took effect 3.5–3.9 wall-seconds after the scheduled minute-45 instant; the rewind rule, which keys on acknowledged sends, covered that. F's recovery is fast in wall-clock terms (2–6 s of script once the hold ends) and slow in operator terms, which is the edition boundary showing up exactly where the pre-reg said it would.
- **BC1**: `restart: on-failure` did not bring the container back after `docker kill` (RestartCount 0, status `exited` for the whole 30 s hold), so the operator needed one `docker start`. Docker behaved as if `docker kill` were an operator stop rather than a failure, which is a fair caution for anyone counting on a restart policy as their supervisor.

One threat the battery did not exercise: because Feldera's HTTP egress is not durable and the frozen rewind only re-sends from the oldest open window, an alert the pipeline emitted in the instant before a kill, but which the drain had not yet read, would be lost and not regenerated. It did not happen here (n=1 per fault, and the kill fell in an alert-free stretch), and the rule does not protect against it.

|---|---|---|---|---|
| B | 2.294 / 2.385 / 2.269 | **2.312** | 2.2% | 60–63% |
| S | 0.265 / 0.225 / 0.228 | **0.239** | 7.5% | 23–28% |
| F (EDITION-BOUND) | 0.105 / 0.105 / 0.105 | **0.105** | 0.0% | 0.3–12.5% |
| BC | 2.250 / 2.380 / 2.212 | **2.323** | 3.1% | 63–68% |

July pooled p50 was S 0.260 s and B 2.271 s, so both July arms reproduce. F's flat 0.105 s is the 2-second `LATENESS` bound expressed on a 20× clock (2 / 20 = 0.1 s) plus a few milliseconds of compute, which tells you what the 1× trial should show for it.

The July latency file says batch's median should be multiplied by the replay factor for a real-time equivalent (it gives B 46.2 s and BC 46.5 s here), and the pre-reg carried that assumption into its 1× predictions. I think that multiplication is wrong for this baseline. Latency is measured from the instant the window closes, the batch file for that window lands at that instant, and what remains is the job's 5-second wall-clock poll, which does not scale with the replay factor. The event-time quantities that *do* scale are the 2-second watermark (S) and lateness (F) bounds. The 1× trial is the direct test, and it bears this out (next section).

**Edition probe (`results/edition-probe.json`, verbatim excerpts).** On the stopped pipeline, `fda set-config smx-detect fault_tolerance at_least_once` returned exit code 1 with `... is not valid due to: enterprise feature: fault tolerance`. The REST equivalent, `PATCH /v0/pipelines/smx-detect` with `{"runtime_config":{"fault_tolerance":{"model":"at_least_once"}}}`, returned `HTTP 400` with `"error_code":"InvalidRuntimeConfig","details":{...,"error":{"EnterpriseFeature":"fault tolerance"}}`, and `exactly_once` returned the same. So the docs' gating claim is now an observed refusal, at config time rather than silently ignored. One of the pre-reg's open items also closed: the OSS pipeline serves Prometheus-format metrics at `/v0/pipelines/<name>/metrics`, so pipeline-level Prometheus metrics are not gated in this image, whatever the architecture page says about Enterprise metrics.

## 1× trial (unattended, n=1)

Ran unattended from 2026-11-03T13:36:48Z to 15:41:55Z (replay 13:37:55 to 15:37:58), all four arms concurrently on the real-time clock, launched by `v2/run_1x_after_faults.sh`. Answer-equality gate: **PASS**, 30/30 on every arm, pairwise identical, 0 missing, 0 extra, 0 duplicates; the S sink topic again held exactly 30 records and the F egress delivered 30 inserts with 0 duplicates and 0 deletes. Moving parts over 698 mid-run samples matched the 20× trials exactly (B 1 unit, S 3 containers / 4 units, F 1 container / 2 units with 12 median and 13 max processes inside, BC 1).

| Arm | p50 at 1× (s) | min / max (s) | Within-trial CV | p50 at 20× (s), for comparison |
|---|---|---|---|---|
| B | **5.198** | 2.695 / 7.153 | 24.9% | 2.312 |
| S | **2.184** | 2.020 / 3.355 | 10.3% | 0.239 |
| F (EDITION-BOUND) | **2.005** | 2.004 / 3.221 | 10.7% | 0.105 |
| BC | **4.641** | 2.134 / 6.637 | 28.0% | 2.323 |

Three things come out of this, and the first matters most for the benefit side of H-IMPL-01.

- **The streaming arms' freshness is mostly their own lateness bound, which is event time.** S at 2.18 s and F at 2.005 s are the 2-second watermark and the 2-second `LATENESS` playing out on a real clock, plus about 0.18 s (S) and 5 ms (F) of engine and sink time. At 20× the same bound costs 0.1 s, which is why both arms looked sub-second there. This is the "waterline delay" freshness cost the pre-reg asked to report for `emit_final`, and Flink's watermark carries the same cost.
- **Batch does not get 20 times slower at real time.** B's p50 went from 2.3 s to 5.2 s, not to the 25–60 s the pre-reg predicted from July's real-time-equivalent multiplication. Decomposing B's alerts, the job's poll and query took a median 2.9 s from file landing to alert (the 5-second poll, as at 20×), and the remaining 2.3 s is the lander writing each file about 2.3 s after its window closed, a lag that was 0.0 s at 20×. That lag is in the harness, not the batch job, and it looks like host timer behaviour: at 1× the lander makes one `time.sleep` of about 58 s per window, and a direct test on this host (`time.sleep(58)`) overshot by 3.1 s, while at 20× its sleeps are about 3 s and the lag measured 0.0 s. So B's and BC's 1× figures include roughly 2.3 s of WSL sleep overshoot that a real file collector would not add.
- **So the freshness gap the streaming stack buys is far smaller on a real clock than July's framing implied.** For this detection, whose alerts cannot fire before a 60-second window closes on any arm, S beats B by about 3.0 s at the median (2.18 vs 5.20 s, roughly 2.4×), or by about 0.7 s once the lander's sleep overshoot is set aside. July's "roughly 8–9× freshness improvement" was a 20×-clock figure, and its real-time-equivalent column (B ≈ 41–48 s) double-counted, because this latency baseline starts at the window close and the batch job's remaining delay is a wall-clock poll that does not scale with the replay factor. I am treating that as a measurement-model finding about the carried assumption, not as a reason to rescore any frozen prediction, and the P4 misses below stand as misses with their measured numbers.

## Frozen decision rules

The three complexity axes, as the pre-reg defines them (moving parts = engine + sink units, median of mid-run samples; config LOC; recovery steps summed over the arm's frozen faults):

| Arm | Moving parts | Config LOC | Recovery steps | Ratio to B (moving / LOC / steps) |
|---|---|---|---|---|
| B | 1 | 131 | 3 | 1 / 1 / 1 |
| S | 4 | 197 | 4 | **4.00 / 1.504 / 1.33** |
| F (EDITION-BOUND) | 2 | 61 | 7 | **2.00 / 0.47 / 2.33** |
| BC | 1 | 156 | 1 | 1.00 / 1.19 / 0.33 |

**MOVE H-IMPL-01 toward 2/5.** All three legs hold: S is 4× B on moving parts (≥ 2× needed), S needs more recovery steps than B counting all three batch faults (4 vs 3), and post-recovery correctness was measured on both arms with the output files present and growing. On exact arithmetic this is the only H-IMPL-01 rule that fires.

**FALSIFIER — a knife-edge I am reporting rather than resolving.** Its first leg does not fire (B's 3 steps are fewer than S's 4). Its second leg asks whether S lands within 1.5× of B on two or more axes. Recovery steps are within (1.33×). Config is 197 / 131 = **1.504×**, which is outside 1.5× on exact arithmetic, but the binding pre-reg itself carries that figure as "1.50×", and July's RESULTS treated it as the one near-parity axis. So the result depends on a reading the frozen text did not settle:

- *Exact arithmetic*: S is within 1.5× of B on one axis (steps). The falsifier does not fire, and MOVE fires alone.
- *The pre-reg's own rounding* (1.50× counted as within): S is within 1.5× on two axes (config and steps). The falsifier and MOVE then fire together, a combination the frozen rules never anticipated.

The margin is less than one line of config (1.5 × 131 = 196.5 against S's 197). The step axis is fragile too: B's total of 3 rests on B3 scoring 2 steps under my byte-truncation reading of "half-length (non-atomic write)" (Deviation 13). A row-level half file would not crash the job, B3 would score 0, B's total would be 1, the step ratio would be 4×, and MOVE would fire alone under either reading. I think the owner and the karen → hypothesis-validator → contradiction-detector gate should make this call, not the bench author, so the confidence change is **staged, not applied**. My own read is that the direction (more running infrastructure and more recovery work for the streaming stack) replicated, and that any move to 2/5 should be quoted with this knife-edge attached, and stay direction-only with magnitude at D as the rule says. The benefit side should travel with it, as the pre-reg requires: on a real clock the streaming stack bought about 3 s of median freshness on this detection (2.18 s vs 5.20 s), not the order-of-magnitude gain the 20× numbers suggested, which makes the cost-for-freshness trade look less favourable to streaming than July's write-up did.

**HOLD and rescope to broker-plus-cluster stacks.** Does not fire. It needs F within 1.5× of B on two or more axes, and F is within on config only (0.47×); it is 2× on moving parts and 2.33× on recovery steps.

**BC rule.** S vs BC on moving parts is 4.00×, so S-vs-B's separation on moving parts survives the containerised batch arm and is not narrowed to "against a containerless batch job." Scored against BC instead of B, the frozen rules read the same way: S is within 1.5× of BC on one axis only (config, 1.26×; moving parts 4×, steps 4 vs 1), and MOVE's legs hold against BC (4× moving parts, 4 > 1 steps, correctness measured).

**Refinement ("the premium moves into platform dependence").** None of the three frozen outcomes fires.

- *SUPPORTED* needs F within 1.5× of B on at least two axes. F is within on config only, so the infrastructure-shrink half fails, even though the dependence half holds cleanly: F's dependence score of 2 exceeds B's and S's 0 through a paid-gated recovery feature, and F's OSS recovery costs more steps than S2 (4 vs 2).
- *NOT SUPPORTED, premium genuinely reduced* needs the same shrink plus S2-level recovery on OSS. Neither holds.
- *NOT SUPPORTED, premium not reduced* needs F at or above S on two or more axes. F is above S only on recovery steps (7 vs 4) and well below it on moving parts (2 vs 4) and config (61 vs 197).

So on this detection the refinement is indeterminate under its own frozen rules. Reading the numbers rather than the rules, Feldera OSS did halve the running units against Kafka + Flink (though not the footprint, where its one image is the heaviest thing on the host) and cut the config to under a third, while moving the recovery burden onto the operator and the input source, behind a feature that only an Enterprise licence key unlocks. That reads to me like a partial version of the refinement: the premium moved, but only partly, and part of what moved went into operator steps rather than into platform dependence alone. For H-STREAMING-02's claim class, Feldera gives a single-host, single-shape data point that an incremental engine lowers the standing infrastructure and config cost on this shape and does not, on its free edition, lower the recovery cost.

## Exploratory, not pre-registered: B2x and B3x (minute-44 window)

The frozen B2 and B3 faults perturb the minute-45 file (window starting base + 2,700 s), and that window holds no ground-truth alert; the nearest alerts are at base + 2,640 s and base + 2,880 s. So B2's frozen "the late window's alert is emitted late but present" clause cannot be tested at minute 45, and B2 and B3 can only show a failure through steps, not through a missing alert. To see what the frozen faults would have shown on an alert-bearing window, I ran the same two faults on the minute-44 file (base + 2,640 s, one ground-truth alert) as B2x and B3x. They change no prediction and no decision rule.

| Fault (exploratory) | Operator steps | Post-recovery correctness | What happened |
|---|---|---|---|
| B2x late file, minute 44 | 0 | **29/30: 1 missing** (`user00705`, `198.51.100.9`, window base + 2,640 s), 0 extra, 0 dup | the file landed 8.84 s late, after the job had processed the next two windows; the job only looks at windows newer than its last processed one (plus a one-window look-back that ran before the file existed), so the late file was never read and the alert was silently lost. No error, no log line, exit code 0 |
| B3x truncated file, minute 44 | 2 | 30/30, 0 dup | identical to B3: DuckDB raised on the truncated file, the job exited 1, and the two-step restart recovered the full answer once the complete file was in place |

The frozen B2 (minute 45) came out the same mechanically, since its late file was also never read, but no alert was at stake there, so it scored 0 steps and 30/30. Read together, B2 and B2x say the batch arm's late-data failure is the quiet kind: zero operator steps because nothing tells the operator anything is wrong, and a missed detection whenever the late file carries one. That is a real batch failure class, and it is invisible to a step count, which is worth carrying into any writeup that leans on the recovery-steps axis.

## Deviations from the pre-registration (dated 2026-11-03)

Each of these is a place where the run could not follow the frozen text literally, or where the text left an implementation choice open. None changes a frozen prediction or decision rule.

1. **Image-bytes basis.** The pre-reg says July's image figures are uncompressed `docker image` sizes. On this daemon (containerd image store, `driver-type io.containerd.snapshotter.v1`) the command July used, `docker image inspect --format '{{.Size}}'`, returns content size: 238,880,881 bytes for `apache/kafka:4.3.1` against 686 MB unpacked. I kept July's command as the scoring basis for P1 (so F is compared with S on the same basis, 2,559,070,153 vs 913,070,380) and report unpacked sizes from `docker system df -v` alongside, at the three significant figures that command gives.
2. **Where `LATENESS` sits in the F program.** The frozen design puts `LATENESS INTERVAL '2' SECONDS` on the event-time column of the `append_only` table. The corpus carries event time as a BIGINT `time` field, and TUMBLE needs a TIMESTAMP, so the program derives `event_time` in a local view. With `LATENESS 2` on the BIGINT table column, the compiler accepted the program but refused `emit_final`: `Could not infer a waterline for column 'alerts'.'window_start' which has an 'emit_final' annotation`. Moving the same 2-second bound onto the derived column with Feldera's view-level statement, `LATENESS auth_ts.event_time INTERVAL 2 SECONDS`, compiled, and `emit_final` then worked as the primary output mode. The input stays byte-identical to the other arms. This is the "waterline inference for TUMBLE's window column" risk the pre-reg named, resolved without the fallback, and it is itself a small dialect finding: the lateness has to sit on a column whose type the window function accepts.
3. **BC process layout.** The pre-reg packages `land_microbatches.py` and `batch_job.py` together in the BC image; both are in it, but the container runs only `batch_job.py`, and the lander runs on the host as harness, exactly as it does for B. Running the lander inside the container would make the BC1 container kill also kill the replay harness, which would confound the fault.
4. **Four arms concurrently.** The pre-reg says the 1× trial runs "all three arms concurrently"; BC was added at freeze, so every clean trial, 20× and 1×, ran all four.
5. **`busybox` pin.** The July S compose names `busybox:latest` for its two one-shot volume-ownership init services. `busybox` was never pulled during this run (the local image, id `sha256:fd8d9aa6…`, was used as-is in the three 20× trials); after the 20× trials I pinned both lines to `busybox@sha256:fd8d9aa63ba2f0982b5304e1ee8d3b90a210bc1ffb5314d980eb6962f1a9715d`, the same image, so faults and the 1× trial reference it by digest. Line count unchanged (197).
6. **Batch drain timeout at 1×.** `batch_job.py` exits after `--max-idle-ticks` consecutive 5 s ticks with no new file. July's 6 ticks (30 s) suits 20×, where a file lands every 3 s; at 1× a file lands every 60 s and the job would exit after the first gap. For the 1× trial only, B and BC ran with 30 ticks (150 s). This is drain detection, not detection logic, and the BC compose file now reads it from `SMX_BC_IDLE_TICKS` (default 6), with no line-count change.
7. **F recovery: stale status after a manager restart (found in smoke).** After `docker start smx-feldera`, the first `GET /v0/pipelines/smx-detect` reads returned the pre-kill `Running` from the manager's embedded database; a second later the manager reconciled to `Stopped` with `RunnerCheckError: "The pipeline-manager and this pipeline were previously terminated. Start the pipeline again."` The first smoke attempt trusted the stale `Running`, re-sent too early, and got `HTTP 503 PipelineInteractionNotDeployed`. The recovery helper (`faults/_feldera_restart_pipeline.sh`) now counts the pipeline as back only when `/stats` answers with an `incarnation_uuid` different from the pre-fault one, and it issues `POST /start` when it sees `Stopped`. That `Stopped` state and the operator start are the finding: on OSS, a container restart does not bring the pipeline back by itself.
8. **F recovery: errexit trap (found in smoke).** The same `set -e` command-substitution trap July's README documents for `recover_taskmanager.sh` killed the first fixed helper on a 503; fixed with `|| true` on the polling assignments.
9. **F2 kill target (found in smoke).** `docker top` reports PIDs in the daemon's namespace, which the host cannot signal on this setup (`kill: (269431): No such process`). F2 now looks up the pipeline process's PID inside the container (scanning `/proc/*/cmdline` for the `local-runner/pipeline-…/program_…` binary) and sends `docker exec smx-feldera kill -9 <pid>` to that one explicit PID. F2 was therefore isolatable and was not dropped.
10. **F step counting.** The frozen F1 rule names four operator actions: restart the container, restart the pipeline, compute the rewind point, re-send. `recover_f1.sh` has exactly those four `# Step N:` markers, with the wait for manager health folded into step 1 and the wait for the sink adapter to re-attach folded into step 2, the same "act, then wait until it answers" convention July's `recover_broker.sh` uses. The sink wait is needed because HTTP egress is not durable: rows a view emits while no client is connected are gone, so re-sending before the drain re-attaches would lose alerts. F2 has the same steps minus the container restart (3).
11. **B2 smoke record.** `results/v2/faults-smoke/B2/result.json` shows `output_grew_after_recovery: false`; that is a measurement bug in the smoke harness (it counted rows after the lander had already finished), fixed before scoring by timing the count from the alert timestamps. The scored B2 shows `true`.
12. **B2 timing.** "Lands only after the job has processed the next two ticks" is implemented as: the minute-45 file lands once the job's own state file shows `last_window_processed ≥ W + 2`, i.e. the job has processed the next two windows' files (`v2/land_faulty.py`).
13. **B3 meaning of "half-length (non-atomic write)".** Implemented as a byte-level truncation: the first half of the window's Parquet bytes is written straight to the final file name (which a reader can observe), and 30 wall-seconds later the complete file replaces it atomically. DuckDB rejects the truncated file (`InvalidInputException: No magic bytes found at end of file`) and the bare job exits with code 1, so B3's recovery is a written two-step procedure (`faults/recover_b3.sh`: wait until the file reads as Parquet, restart the job). A row-level half file (valid Parquet with half the rows) would instead undercount silently; that variant was not run.
14. **Duplicates on S2.** Both sink adapters deduplicate on the alert key, so an engine-level duplicate never reaches the alert file. To keep the pre-reg's "duplicates between 0 and 3" measurable, duplicates are reported twice: in the file (always 0) and raw at the engine (S: `smx-alerts` end offset minus 30; F: duplicate inserts on the egress stream).
15. **S1 producer behaviour.** The frozen rule says the producer pauses on send failure and resumes from the first unacknowledged event. The July producer was used unchanged: its librdkafka client queues unacknowledged messages and retries them in order until the broker returns (well inside its default 300 s message timeout), and it logged 0 delivery errors, so the rule held without new pause code.
16. **Fault scheduling.** The battery ran as parallel lanes with no shared containers or directories (S1 then S2; F1 then F2; each batch fault and BC1 in its own lane), so host contention may have nudged wall-clock figures. Step counts and correctness are unaffected.
17. **Wall-clock with a held outage.** The pre-reg holds the outage for 30 s before recovery starts, so "kill to infrastructure restored" includes those 30 s. I also report the recover script's own duration, which is what July's 18.14 s / 21.46 s / 0.02 s measured.
18. **BC1** is not in the frozen battery table but is defined by P3-BC ("container kill"); it ran on the battery's terms (`docker kill smx-bc-batch` at minute 45, 30 s hold).
19. **B2x and B3x** were added as exploratory faults, outside the pre-registration (see that section).
20. **F runtime config.** The deploy script passes an empty `runtime_config`, so the pipeline ran on the manager's defaults (8 workers). Each clean trial deployed a fresh container; deploy plus SQL-to-Rust compile plus start took 24.71, 22.65 and 22.68 s on the three 20× trials.
21. **Run order.** The 1× trial ran last, after the fault battery, rather than interleaved; it started automatically when the scored F lane exited, so no other bench load overlapped it.
