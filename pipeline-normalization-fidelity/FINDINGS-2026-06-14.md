# Pipeline normalization-fidelity (#10) — Tenzir arm scored (2026-06-14)

First scored arm of the bench. Tenzir's **shipped** library OCSF mapping was run, unedited,
over the pinned corpus; this is what the tool's published mapping actually delivers, not a
hand-written one. Tier B, single host. Versions pinned: Tenzir **6.0.0**, library commit
**671e049** (`zeek::ocsf::map`), OCSF **1.8.0**. Per-source scores in `results/results.json`
+ `results/RESULTS.md`; method + the blocked-then-unblocked history in `STATUS-2026-06-14.md`.

## Result — Tenzir shipped mappings vs the gold

| source | OCSF class | coverage | field | value | class | activity_id |
|---|---|--:|--:|--:|--:|--:|
| zeek_conn | network_activity 4001 | 100% | 80% | 92% | **100%** | **17%** |
| cloudtrail | api_activity 6003 | 0% | — | — | — | — |
| sysmon | process_activity 1007 | 0% | — | — | — | — |
| auth | authentication 3002 | 0% | — | — | — | — |

**Zeek conn (the one source Tenzir ships a JSON-consumable mapping for):** the mapping nails
the OCSF *class* (100% — correctly Network Activity 4001) and most *values* (92%), covers every
gold field somewhere (100% coverage), but two real gaps show up that field-level scoring alone
would hide:
- **activity_id 17%** — the mapping does not derive the OCSF activity from Zeek's `conn_state`,
  so on 83% of records the activity classification diverges from the faithful gold. A consumer
  filtering on `activity_id` (open vs close vs reset vs fail) would mis-bucket most connections.
- **field fidelity 80%** — `history`, `service`, and `uid` land in `unmapped` rather than a typed
  OCSF attribute (each on all 100k records). `value` 92% is mostly the `ts` representation (the
  mapping's OCSF time differs from the gold's canonical value on every record) plus a few
  `duration` cases.

**The other three sources are 0% coverage — and that is the P1 finding, not a harness gap.**
Tenzir's Community Library ships OCSF mappings for Zeek and Sysmon and an `amazon` package, but:
- **cloudtrail** — the `amazon` package ships route53 / security_lake / vpc_flow only; there is
  no CloudTrail-management-events → OCSF API Activity operator, so nothing maps.
- **sysmon** — the shipped `sysmon::ocsf::map` calls `parse_winlog()`; it expects raw Windows
  EVTX/XML, not the pre-parsed JSON the corpus (and most EDR shippers) carry, so it does not
  consume this input shape.
- **auth** — a generic auth source by design; no vendor ships a mapping for these field names.

**Caveat on the failure-class table** (`results/RESULTS.md`): the "100%" failure-class cells on
the three 0%-coverage sources are no-output artifacts (with nothing emitted, every probe
trivially "reproduces"), not real reproductions — only the zeek_conn row (entity_role 0%,
observables_flattening 0%) is a genuine measurement, and there Tenzir does NOT reproduce those
crosswalk failure classes.

## Vector arm — no shipped OCSF mapping at all (P1 confirmed across two tools)

Vector **0.56.0** (`timberio/vector:latest-alpine`) ships **no OCSF support** — no OCSF component
in `vector list`, no OCSF strings in the binary, no OCSF VRL function. So its coverage is **0% on
all four sources**: a faithful run would require hand-written VRL, which measures the author, not
the tool (the bench's stop rule scores no-shipped-mapping as 0% coverage, reported separately from
fidelity). Not run — there is nothing shipped to run, and that absence is the result.

This makes P1 a **cross-tool** finding, not a Tenzir quirk: of the two open tools tested, Tenzir
ships a usable mapping for one of four sources (Zeek-JSON; Sysmon is XML-bound, CloudTrail/auth
absent) and **Vector ships none**. Shipped-mapping *availability* — not per-field fidelity — is the
binding constraint on "OCSF normalization at-source." Cribl (the third tool, needs an account to
pull its OCSF Pack) is the one that advertises a packaged OCSF mapping and would test whether a
mapping-focused product closes the gap; it remains deferred.

## So-what

- **For Matrix Component 4 ("OCSF normalization at-source"):** Tenzir's shipped mapping is real
  and gets the easy 80% (class + most values) but leaves a measurable semantic gap on the part
  that matters for detection — the activity classification — and ships no mapping at all for two
  of four common security sources in their consumable shape. "Maps to OCSF" is a coverage claim,
  not a fidelity guarantee, and this bench is the measurement that separates the two.
- **P1 (coverage ordering / availability) is the headline:** shipped-mapping availability is the
  binding constraint, not per-field fidelity — three of four sources have no usable shipped
  Tenzir mapping. Cribl and Vector arms (deferred — Cribl needs an account, Vector is mostly
  non-official VRL) would test whether that availability gap is tool-specific or general.

## Scope, honestly

One tool (Tenzir), one faithful source (Zeek conn), shipped mapping run unedited, versions

commit 671e049; re-run on a newer library before repeating. Cribl + Vector arms remain to run.

## Erratum (appended 2026-11-15; the pre-registration in README.md and the text above are unchanged)

The zeek_conn row above misdescribes what Tenzir's shipped mapping did. Each point below was re-derived on 2026-11-15 over all 100,000 records from the saved inputs, by `../ocsf-1.9-rescore/scripts/erratum_derive.py` (output `../ocsf-1.9-rescore/results/erratum-derivation.json`). Inputs: `_work/zeek_conn.corpus.jsonl` (sha256 `30f624f1…aa1bd`) and `_work/zeek_conn.gold.jsonl` (sha256 `f6e54d5c…742c1`), both equal to `_work/corpus_manifest.json`; `results/tenzir_zeek_conn.emitted.jsonl` (sha256 `561ce680…661929c`); the C1 1.8.0 subset plus this bench's ext subset. This erratum states mechanisms only. It does not publish corrected percentages; the pre-registered re-score that produces them is `../ocsf-1.9-rescore/`.

1. **`activity_id` 17% is a gold-key artifact, and the mechanism above is inverted.** The gold pins `activity_id = 6` (Traffic) on every Zeek record (`gen_corpus.py` l.180-181, "6 = Traffic (the conn.log grain)"; all 100,000 gold rows carry 6). Tenzir derives the activity from `conn_state`: S0 → 1 Open (16,697), SF → 2 Close (16,579), RSTO → 3 Reset (16,629), RSTR → 3 Reset (16,716), REJ → 5 Refuse (16,677), OTH → 6 Traffic (16,702). The two agree only on OTH, 16,702 of 100,000, which is the 17%. The sentence "the mapping does not derive the OCSF activity from Zeek's `conn_state`" is wrong: Tenzir derives it and the gold does not. Whether a derived activity or a flat Traffic is the better mapping is a judgement the re-score addresses with a written rule; it is not a Tenzir failure.

2. **Nothing but the bench's own join key went to `unmapped`.** On all 100,000 emitted records `unmapped` holds exactly one key, `_id`, which the bench injects for the join. The statement that `history`, `service` and `uid` "land in `unmapped`" is wrong.

3. **The three "dropped" fields landed on other valid OCSF 1.8.0 paths, with the source value intact on every record.** Zeek `uid` is at `connection_info.uid`, `metadata.original_event_uid` and `metadata.correlation_uid`; `service` is at `app_protocol_name`; `history` is at `connection_info.flag_history`. Each path is present with a value equal to the source value on 100,000 of 100,000 records, and each resolves "full" (every segment transcribed, not the validator's "deep" acceptance) in the merged 1.8.0 subset `score.py` validates against. The gold wanted `metadata.uid`, `app_name` and `connection_info.tcp_flags`; the scorer credits only the gold's chosen path, so the 80% field fidelity measures agreement with the gold's choices. Two gold choices are themselves questionable against the OCSF 1.8.0 dictionary text: `metadata.uid` is described as "specific to the OCSF event itself and … distinct from the original event identifier in the source system (see `original_event_uid`)", and `connection_info.tcp_flags` is typed `integer_t` (header control bits) while the gold puts Zeek's letter string there, which `flag_history` ("For example flags ShAD …") exists to hold. The 1.8.0 subset carries no attribute types, so the validator could not catch the second one. On `service`, the 20,166 records whose Zeek value is `-` (no service detected) carry the literal `-` in `app_protocol_name`, as the gold does in `app_name`.

4. **`ts` is a type-contract deviation, not information loss.** Tenzir writes `time` as an RFC 3339 string with nanosecond digits (e.g. `2026-01-06T14:33:05.181363968Z`) on all 100,000 records, where OCSF types `time` as `timestamp_t`, a long count of epoch milliseconds. Parsed back, the string equals the corpus value at the corpus's own microsecond precision on 100,000 of 100,000 records; the nanosecond digits carry binary-float noise of at most 240 ns. A consumer that truncates the string to milliseconds gets the gold's millisecond value on 99,963 records and a value 1 ms low on 37, because of that noise, while rounding to the microsecond first recovers all 100,000. A strict consumer expecting the OCSF integer will reject or mis-parse every record, so the finding stays, reworded from "mangled" to "type-contract deviation (string where `timestamp_t` requires epoch-ms long)".

5. **The 53 `duration` differences are a rounding-convention tie, not damage.** All 53 are source durations that fall exactly on a half millisecond. The gold uses Python's `round()`, which rounds half to even; Tenzir rounds half up, so it is 1 ms higher on those 53. Both are faithful millisecond conversions.

What stands from the original row: class 100% and the two genuine failure-class measurements (entity_role 0%, observables_flattening 0%). The availability findings for cloudtrail, sysmon and auth (0% coverage, no usable shipped mapping on this corpus) are unaffected. The "class-right/activity-wrong" shape in "Scope, honestly" and the "So-what" bullet about a "measurable semantic gap on … the activity classification" should be read through points 1 to 3 and not repeated.
