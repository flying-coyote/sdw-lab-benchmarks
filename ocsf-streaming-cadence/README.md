# R7 — streaming write cadence: throughput, commit latency, and where DuckLake inlining inverts

*(corrected 2026-11-17: the title says this bench finds "where DuckLake inlining inverts". Against Iceberg no inversion was reached: inline's throughput edge narrows from 3.93× at 5 rows per commit to 3.33× at 50 and 2.13× at 500, and inline is still ahead at the largest cadence. Against DuckLake without inlining, the commit-latency advantage does invert, because inline commit p50 is lower at 5 rows (10.2 vs 11.9 ms), level at 50 (12.1 vs 12.2 ms) and about twice as high at 500 (24.0 vs 12.5 ms, with p95 26.4 vs 14.8 ms), so the crossover sits between 50 and 500 rows per commit. DuckLake without inlining also out-throughputs inline at every cadence (345 vs 273, 3,383 vs 2,427 and 32,970 vs 15,238 rows/s), but the inline arm's timed wall includes a count read after every commit (`run.py:92-109`), so that comparison is not like-for-like. Source: `results/results.json`.)*

## Layout and audit notes (added 2026-11-17)

### Result, and whether it is measured

Measured. 200 commits per cadence on three write contracts; Iceberg writes 200 data files at every cadence and the inline arm writes none, and the inline arm's running count stays exact while the stream writes. Iceberg commit p95 stays near 132 to 136 ms whatever the batch size.

### What would have made it fail

The bench would have refuted the inversion if inline's edge over Iceberg had held or widened at larger batches, or if inline's commit latency had stayed at or below the no-inline arm's at 500 rows per commit. The coherence claim would have failed if the read-while-write check had returned `False` at any cadence.
