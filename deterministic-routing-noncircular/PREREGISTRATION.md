# Pre-registration: deterministic-routing-noncircular

Written before any corpus query was executed on any engine, before the DuckDB oracle computed any answer, and
before the rule stack was asked for a single pick on the new corpus. What I had done before freezing, so a reader
can see what I knew: read draft 20, the H-DETERMINISTIC-ROUTING-01 entry, `deterministic-routing-sim/`
(RESULTS-2026-06-15.md, `route_sim.py`), `engine-join-specialization/` (README, `queries.py`, `run_bench.py`,
`load_tables.py`, results), `soc-query-shapes/RESULTS-ueba-rare-2026-06-15.md`, methodology sections 7a, 7b and 10,
and the T8b and T8c house files. I rebuilt the stack (below), loaded the pinned parquet into Iceberg and the
native MergeTree copies (count-exact per table), generated the corpus, and ran parse checks only (sqlglot parse in
the default, StarRocks, ClickHouse and Trino dialects, and DuckDB `EXPLAIN` bind checks over the parquet; 84 of 84
pass all five). I profiled the parquet for parameter value domains (ports, protocols, criticality levels, the
conn/dns time span), which feeds the generator's literals and nothing else.

## Question

The June routing simulation scored 11 of 11 on templated shapes, but its corpus was the ten measured shapes, so
that number shows the rules encode the winner table and nothing more. Off its own training shapes, on a
distribution generated by a documented procedure and executed on every engine for ground truth, does the
unchanged rule stack (R1 time tier, R2 AST shape, R3 catalog consult, the June `WINNERS` table) still place
queries on the measured winner, and above all does it still keep queries off the engine where they fall off a
cliff? Secondary: does a $0 LLM router do better or worse at the same job, how stable is its answer across
repeated trials, and what does it add per decision in latency?

## Instrument

### Rule stack under test (unchanged)

`../deterministic-routing-sim/route_sim.py`, sha256 `1ce786087522cd774653d51340c926901b2574eec01d9ba6a518d1db37603683`,
imported by path by `score.py`; no line of it changes. Its `WINNERS` table, shape rules, time-column vocabulary
(`ts`, `day`, ...), table vocabulary (`iocs`, `dim_host`) and `NOW_REF = 2026-06-15` stay as written.

### Corpus (item 1)

`queries/corpus.json`, **84 queries, sha256 `8af784cc6732968b92f2bb26a70194ac6f42f6c60b636b599a5a15a848632033`**,
written by `gen_queries.py` (sha256 `5e9337981ad7cac5b2031883b84d9306bc70978cc6acb7a4b04f9013e82a816e`, seed 20261115).
Procedure: twelve families of parameterised templates written for this bench on the real ejs schema (TPC-H SF10
plus `soc.conn`, `dns`, `assets`, `ioc`, `conn_enriched`); none of the eleven engine-join-specialization texts is a
template, though several families are deliberately the same broad kind of work so the rules get a fair chance.
Within a family the template index cycles deterministically and every parameter (tables, join path, group key,
filter values, thresholds, bucket width, LIMIT) is drawn from the seeded RNG. The family label is the generator's,
assigned before any routing. Families and counts:

| family | n | what varies |
|---|---|---|
| scan_agg | 8 | single table, one GROUP BY level; conn, dns, lineitem, conn_enriched |
| point_lookup | 4 | filter + ORDER BY unique key + LIMIT on conn, dns, lineitem |
| dim_enrichment | 8 | fact x small dim, one join (conn/dns x assets, lineitem x supplier, orders x customer) |
| ioc_match | 8 | JOIN form, IN-subquery form, dns answers vs ioc |
| two_stream | 6 | per-host aggregate of conn joined to per-host aggregate of dns (half use exact COUNT(DISTINCT)) |
| large_large | 6 | conn x dns time-bucket correlation (60/300/600 s), conn x conn_enriched on uid, lineitem x orders |
| join_3to4 | 10 | 3- and 4-table TPC-H paths incl. the customer-orders-lineitem-supplier path with the dual `c_nationkey = s_nationkey` key (the q5-class many-to-many edge), plus conn-assets-ioc |
| join_5to6 | 6 | 5- and 6-table TPC-H paths, with and without the dual key |
| topn_agg | 8 | 2- and 3-table aggregation with ORDER BY agg DESC LIMIT n or HAVING |
| correlated_exists | 8 | EXISTS / NOT EXISTS on orders-lineitem, assets-conn, assets-dns, supplier-partsupp |
| ueba_two_level | 8 | per entity per time bucket, then per-entity peak vs mean flagged in integer arithmetic (`peak * n_buckets > k * total`), on conn and dns, one variant with a dims join; built to return non-empty results |
| window_seq | 4 | lag inter-arrival and row_number first-seen per host |

SQL discipline is the original bench's: one ANSI text per query, `$table` placeholders substituted per arm, every
derived table aliased, deterministic ORDER BY under every LIMIT, exact aggregates in outputs (count, sum, min,
max; COUNT(DISTINCT) only inside `two_stream` subqueries, where ClickHouse's default is `uniqExact`), no AVG or
float stddev in outputs, no engine-specific functions. After the freeze no query is rewritten: a dialect failure on
an arm is a DNF of type `dialect`, and a query no arm answers correctly is excluded from scoring and reported N of M.

### Anchors

The eleven original texts (`ejs_queries.py`, a byte-identical copy of `engine-join-specialization/queries.py`,
sha256 `113e1d75...d959a0`) run first on every arm against the original ground truth
(`queries/anchor_ground_truth.json`, byte-identical copy, sha256 `2021dc3a...45cbf`). They are not part of the
corpus score. They check whether the rebuilt stack reproduces June, above all the native q5 timeout.

### Engines and stack

Rebuilt under its own compose project (`compose.yml`, project `drn-bench`, containers `drn-*`) because no ejs
container, volume or image survived; nothing in `engine-join-specialization/` is written. Arms, as in the original
bench minus Dremio: `starrocks` (StarRocks `allin1-ubuntu:4.1-latest`, digest `7f6041f6...96f8`; exact
`current_version()` recorded in the raw file; the June run was 4.1 of an earlier date, declared drift),
`clickhouse_iceberg` and `clickhouse_native` (ClickHouse **26.5.1.882**, digest `07afc18d...3bf5`, pinned to the June
version because the native q5 cliff is tied to 26.5's join reordering), `trino` (Trino 481, digest `5b5e0a97...4006`).
Catalog Nessie `latest` (digest `d3e30c5d...32f5`, IN_MEMORY), object store MinIO from `cgr.dev/chainguard/minio`
(digest `18c8fa28...ef3e`) because `minio/minio` and `minio/mc` no longer pull from Docker Hub. Same configuration as
June: 24g per engine, one engine running at a time, ClickHouse `max_memory_usage` 18e9, `ORDER BY tuple()` native
tables, the planted sort-last metadata pin for `icebergS3`, StarRocks `new_planner_optimize_timeout` 60000.

**Dremio** is a declared exclusion from every scored number: the rules never pick it, every lab publication
withholds its results under its benchmark terms, and its pass adds about an hour and a setup surface. If time
remains after every other step it may run as a withheld arm, written to `results/withheld/` and never scored.

### Protocol

Per arm and query: 1 discarded warmup + 5 timed trials, client-side wall time from `drn-lab` over each engine's
persistent protocol, 300 s per-query timeout enforced client- and server-side, two strikes = DNF
(`timeout | resource | dialect | error`). The 1/5/15-minute load average is recorded with every execution because a
sibling DuckDB bench may share the host; timings are indicative, medians of 5, and I make no claim from a gap
inside the CV gate. Answer equality first: every corpus answer is compared with a DuckDB 1.5.3 oracle over the same
pinned parquet (`oracle.py`, `memory_limit 8GB`, 4 threads, run after the freeze), normalised and toleranced exactly
as the original bench (`normalize`, `answers_equal`, plus or minus 0.02).

### Ground truth per decision

Every query is scored in two cells. **Hot** (recent window, native MergeTree holds the data): eligible
{starrocks, clickhouse_iceberg, clickhouse_native}. **Cold** (deep history, Iceberg only): eligible
{starrocks, clickhouse_iceberg}. This is the June simulation's own tier model. Secondary universe: add `trino` to
both cells. In each cell:
- valid engines: completed and oracle-matching; best = lowest median among valid engines;
- acceptable winners (tie-tolerant): valid engines whose gap to the best is within max(CV_best, CV_engine), the
  house claim gate; strict winner = the best alone;
- **cliff** on an engine: a DNF, or a median at least 10x the best and at least 5 s (soft cliff); a wrong answer
  is reported separately as `silent_wrong`.

Outcome of a pick: `catastrophic` (pick is a cliff), `silent_wrong`, `ineligible` (pick not allowed in the cell),
`correct` (pick in the acceptable set), otherwise `minor`. Regret = pick median minus best median, with a DNF priced
at 300 s minus best (a floor, since the timeout truncates it).

### Scorings

- **S1 verbatim (strictly unchanged):** `Router(use_catalog=True).route()` on the executed text with bare table
  names; R1 decides the tier from the text. Because the real schema's time columns are `o_orderdate` and an epoch
  double `ts`, I expect R1 to fall to `cold`/`default` for nearly every query; the pick is scored in both cells.
- **S2 forced tier (headline for cliff avoidance):** unchanged `Router.shape()` plus `WINNERS[shape][cell][0]`,
  scored in the hot and the cold cell. This is the rule stack's R2 with R1's answer supplied, which is the only way
  the native tier, and so the cliff, can enter.
- **S3 vocabulary binding (secondary, labelled):** S2 after renaming `ioc` to `iocs` and `assets` to `dim_host` in
  the routed text, the sim's table vocabulary; a deployment binding, not a rule change.
- **Baselines:** always-StarRocks, always-ClickHouse-Iceberg, always-native (hot cell only), each with accuracy,
  cliffs hit and regret, because the draft leads with the one-front-engine default.

Every summary is reported per cell and per family before any pooled figure (methodology section 10, per-stratum).

## Hypotheses and what would falsify them

Predictions are mine, written before any result, with rough probabilities.

- **H1 placement.** S2 tie-tolerant placement accuracy on the corpus is at least 0.90 in both cells (the
  hypothesis's own threshold). *Falsified* if below 0.90 in either cell. I expect it to fail (about 70%), because the
  shape classifier keys on table names and join counts the real schema doesn't match, and the hot cell asks it to
  separate engines a few tens of milliseconds apart.
- **H2 cliff avoidance (headline).** Across both S2 cells the rule stack makes zero catastrophic picks.
  *Falsified* by one or more. I expect it to hold in the cold cell (about 80%) and to be at real risk in the hot
  cell (about 50%), because R2 sends any 3-to-4-table join to native MergeTree and the dual-key 4-table paths are the
  q5-class edge.
- **H3 one front engine.** Always-StarRocks, in the cold cell, has no cliff and a mean regret of at most 0.25 s per
  query against oracle routing. *Falsified* by any StarRocks cliff or a mean regret above 0.25 s. Expect hold (about 65%).
- **H4 UEBA misclassification.** The rules classify at least 6 of the 8 `ueba_two_level` queries as a flat or
  non-aggregation-depth shape (scan_aggregation, large_large, dim_enrichment), and for a majority of those the
  measured cold-cell winner is StarRocks, so the rule pick (ClickHouse-Iceberg) is a misroute. *Falsified* if the rules
  classify them otherwise, or if ClickHouse-Iceberg wins the majority in the cold cell (the June inversion does not
  replicate). Expect hold (about 60%).
- **H5 within-shape winner stability (the hypothesis's Null).** For every router shape class holding at least 4
  corpus queries, one engine is the strict winner for at least 80% of them, per cell. *Falsified* (the Null supported)
  if any such class falls under 80% in either cell. Expect falsified (about 75%).
- **H6 anchor reproduction.** On the rebuilt stack native q5 again fails (DNF), and the strict winner of the
  non-tie anchors (q3, q5, q9, q18, q21, j1, j4) matches June in at least 6 of 7. *Falsified* if native q5 completes, or
  2 or more anchor winners change. If native q5 completes, the cliff story in draft 20 changes and RESULTS says so first.

### Item 2: LLM-router arm (pre-registered now, run only after every engine pass has finished so CPU inference cannot touch the timings)

- Legs: **local** `gemma4:e4b` (Ollama 0.20.6, the T8b runtime, digest prefix `c6eb396dbd59`), temperature 0.7, per-trial
  seed 1000+trial, `num_thread 8`, thinking off, `num_predict 16`; **hosted** `agy` 1.5.9,
  `--model gemini-4-hydrogen-high`, plan quota, no API spend, its sampling settings not controllable (declared).
- Subsample, fixed now: the `_01` and `_02` query of every family, 24 queries, each in the hot and cold cell, 48
  decisions, **5 trials each** (240 calls per leg). If agy quota cannot cover 240 calls, the agy leg drops to the
  `_01` queries only (24 decisions, 120 calls) and says so; no paid API substitutes for a leg that can't run.
- Prompt: `llm_router.py` (sha256 `c9d5388c307e4e19148c9d0e2d0e7db83d013fe1888a435810b26fe7c233179c`), the same text for
  both legs: neutral one-line engine descriptions, the cell's eligibility, real table row counts, the SQL. The
  `WINNERS` table, any bench timing and any answer never enter the prompt. Closed-set parse of the first line;
  anything else is `invalid` and scored as a miss.
- Metrics per leg, per cell, per family: tie-tolerant and strict placement accuracy against the measured winners
  (modal pick and per-trial mean), catastrophic picks, flip rate (share of trials whose pick differs from the
  decision's modal pick), invalid rate, and added latency per decision (median and p90; agy includes CLI start-up).
  The rule stack's S2 picks on the same 48 decisions are the comparator; its latency is timed over the same
  decisions and its flip rate checked by routing each decision five times.
- **H7.** Each LLM leg's modal-pick tie-tolerant accuracy is below the rule stack's S2 on the same 48 decisions.
  *Falsified* for a leg that matches or beats it.
- **H8.** Each LLM leg has a flip rate above zero; the rule stack's is zero. *Falsified* for a leg with zero flips.
- **H9.** Median added latency per decision is above 1 s for the local leg and above 2 s for agy, against under
  10 ms for the rule stack. *Falsified* for a leg under its threshold.
- Contamination and synthetic-recognition (section 10): the corpus is TPC-H-derived plus synthetic Zeek-shaped
  tables, both plausibly familiar to the models; there is no no-data arm because the task is a placement judgment,
  not recall of an answer. Declared as a limit.

## What would change what

If H2 holds and H1 fails, draft 20's position strengthens in its own terms: the rules are a poor optimizer but a
good cliff guard. If H2 fails, the draft's claim that the shape map "never sends a join-heavy shape to native"
fails off its training shapes, and the cliff-avoidance argument has to be rebuilt around something other than R2.
If H3 holds, the no-router default leads harder. H1 to H6 move no hub confidence on their own; any confidence move
goes through the hypothesis-evidence gate in the hub.

## Re-freeze conditions

The run stops and this file is re-frozen with a dated deviation if (a) the oracle fails on a corpus query (that
query is excluded, not rewritten), (b) an arm cannot start at all, or (c) a harness bug corrupts recorded results.
Anything else is a deviation recorded in RESULTS.md without touching this file.
