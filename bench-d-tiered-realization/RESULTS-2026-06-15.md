# BENCH-D — tiered-realization write/commit-freshness contract (2026-06-15)

Grounded by Gemini batch-2 DR #4, which asserted three hot-tier realization paradigms with distinct
freshness contracts: **File-Write** (Kafka→Flink→Iceberg, "1–5 min"), **SQL/WAL**
(ClickHouse/Druid/Pinot, "ms–sec"), **Never-Write / Catalog-Inline** (DuckLake, "sub-second"). The
full streaming front (Kafka/Flink) is out of scope without that infra; this measures the inherent
**storage write→queryable contract** each paradigm rests on, first-party — turning the DR's asserted
bands into numbers. Tier B, single host; synthetic conn-like rows (structured; aggregate output).

- Catalog-inline = DuckLake (DuckDB 1.5.3, local catalog + parquet)
- SQL/WAL = ClickHouse 26.5.1 native MergeTree INSERT
- File-write = Apache Iceberg append/commit (pyiceberg → Nessie/MinIO)

## Results — write+commit (freshness) and query-after-write, median of 3, ms

| paradigm | 1k wc | 10k wc | 100k wc | query-after-write (100k) |
|---|---|---|---|---|
| DuckLake catalog-inline | 16 | 19 | 80 | 8 |
| ClickHouse WAL | 61 | 72 | 100 | 2 |
| Iceberg file-commit | 71 | 72 | 124 | 290 |

## The finding — DR #4's bands refined

**All three write/commit in sub-second** at the storage layer (≤124 ms even at 100k-row batches). In
particular the **Iceberg commit is ~70–124 ms, NOT "1–5 minutes."** So DR #4's "1–5 min file-write"
band is **not an inherent Iceberg-commit cost** — it is the **Flink micro-batch checkpoint interval**
(a streaming-cadence *configuration choice*) layered on top of a sub-second commit. This bench
isolates the commit from the cadence and shows the two are different things; the "1–5 min" is a knob,
not a property of the format.

**Where the paradigms actually diverge is read-after-write, not commit:**
- DuckLake (catalog-inline) and ClickHouse (WAL) serve the just-written data in **single-digit ms** —
  local storage, no object-store round trip.
- Iceberg (file-write) serves it in **~100–290 ms** (and rising with table size) — the S3 metadata +
  data read is the real cost of the open-format path, and at streaming scale the Flink batch interval
  is added on top. So the file-write paradigm's freshness penalty is **object-store read latency +
  streaming cadence**, not commit latency.

Ordering at the storage-commit layer: DuckLake < ClickHouse < Iceberg (16/19/80 < 61/72/100 <
71/72/124 ms), but all sub-second — the contract differences DR #4 named are real but live in the
read-path + streaming cadence, not the commit.

## Limitations (honest)

- **No Kafka/Flink streaming front** (no infra) — so the end-to-end "1–5 min" file-write number is
  deliberately NOT reproduced; that is the point (the commit cost ≠ the asserted band, and the band is
  a cadence choice). A true end-to-end streaming-freshness arm would need Kafka + Flink + a configured
  checkpoint interval.
- Small batches (≤100k rows), single host, single-snapshot tables; the Iceberg query is a full
  re-scan of a growing table (the query-after-write number is directional, confounded by cumulative
  growth, not an incremental-read measurement).
- Run split across environments (DuckLake + ClickHouse from host via mapped ports; Iceberg from
  inside the ejs network because Nessie returns the internal MinIO endpoint) — same engines/data,
  merged results.

Gate before any hypothesis confidence move. This grounds the BENCH-D leg of the batch-2 DR
reconciliation: the realization-paradigm freshness contracts are real but the file-write "1–5 min" is
a streaming-cadence artifact, not a commit cost — useful for the tiered-realization / hot-tier
framing (don't quote "1–5 min" as an Iceberg property).
